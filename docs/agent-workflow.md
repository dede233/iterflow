# Agent 工作规范

本规范约定本仓库的任务组织、模型分工、资源所有权和交付证据，配合 [AGENTS.md](../AGENTS.md) 使用。它不改变技术栈、业务规则、权限、revision、事务、契约或发布门禁，也不授予部署、数据库操作或远端写入权限。

## 1. 规则、事实与授权

- **长期规范**：`AGENTS.md` 与本规范中的持续工程要求；适用指令冲突按既有优先级处理。
- **历史事实**：执行记录、旧批准、旧测试与部署结果，只证明当时的范围、版本和环境；不能推断当前环境状态。
- **当前授权**：本次会话中仍有效的用户目标、允许操作和明确限制。旧版本的一次性合并、发布、迁移或部署批准不能复用。

同一范围内有效授权持续生效，直接推进必要工作，不逐项要求审批。新需求先核对现有授权；只有缺少必要信息、核心业务规则冲突或确需超出授权时才询问，并说明具体缺口。局部阻塞时继续互不依赖的已授权工作。

## 2. 先说明任务，再实施

协调者先阅读适用规范、当前任务及相关规格，检查工作区基线，然后在执行前展示精简任务表。复杂性、推理需求、风险和修改范围分别判断：文件少不等于低风险，任务大也不等于每步都需最高强度。

表中说明依赖、执行者及模型强度理由、验收和结果；同步列出允许修改文件、可用环境资源与非目标/禁止项。小任务只需一行，不为填表拆出多名代理。任务表用于沟通和追踪，已授权工作无需等待逐项审批。

```markdown
目标 / 当前授权：……
允许文件：具体文件或明确目录；范围变更先由协调者核对授权并更新
允许环境资源：本任务数据库/schema、账号、容器、端口、浏览器会话等；无则写“无”
非目标 / 禁止项：如不改业务规则、不操作保留数据库、不推送/部署

| ID | 任务与修改范围 | 复杂性 / 推理需求 / 风险 | 依赖 | 执行者、模型强度与理由 | 验收 | 状态 / 结果证据 |
| --- | --- | --- | --- | --- | --- | --- |
| T1 | …… | 简单或标准或复杂 / …… / …… | 无或任务 ID | …… | 可观察的完成条件 | 待开始 / — |

资源所有权：资源标识 → 唯一 owner；并行上限、重型资源限制：……
```

状态统一为：**待开始 → 执行中 → 待验收 → 完成**；遇到阻塞或取消时如实标为 **阻塞 / 取消**，注明原因、可继续部分及恢复条件。“实现结束”不等于“完成”，依赖任务在需要的产物通过验收后才解锁。

## 3. 模型与角色

用户使用 **Astra 作为主模型、6.1 Sol 作为子代理**。模型和推理强度由运行时配置决定；Markdown 只能约定分工，不能自动切换主模型或改变实际强度。派发时核对工具可设置的模型/强度并记录实际配置，不声称未发生的切换；必要配置不可用时说明限制并调整分工，不能虚报已按配置执行。

当前工具标识：Astra 为 `gpt-6-astra`，6.1 Sol 为 `gpt-6.1-sol`；以当次工具实际可用选项为准，不通过本文修改运行配置。

| 工作类型 | 默认承担者 / 强度 | 选择理由与边界 |
| --- | --- | --- |
| 规范理解、拆分依赖、调度、集成、最终验收 | 主模型 Astra / high | 保持全局目标、约束与证据一致；用户在运行时选择主模型配置 |
| 简单、边界清晰的实现或验证 | 6.1 Sol / high | 可独立完成、验收明确；一个代理可同时实现并执行相应测试 |
| 标准任务 | 6.1 Sol / xhigh | 默认选择；在既定规格内完成常规多文件实现、测试和修复 |
| 标准任务中有额外推理需求的部分 | 6.1 Sol / ultra | 必须说明额外推理需求及采用理由，例如需联合验证多个明确约束；不要只写“更稳妥” |
| 架构决策、困难调试、需求模糊或影响重大 | Astra / high | 先解决关键判断、边界或根因，再把清晰且可验收的后续执行交回 Sol |

Sol 能够可靠处理的实现工作应优先委托 Sol，不因主模型是 Astra 而由 Astra 包办。模型分配依据具体工作；风险高时加强分析和验证，不机械地把全部实现交给 Astra。Sol 已可靠完成并有可核验证据的工作，由协调者检查和集成，不交给 Astra 重做一遍。

角色与代理数量分开：协调、实现、测试、审查是职责，不要求各占一个代理。只有依赖可解耦、资源可隔离、并行收益明确且当前指令允许时才启动多个代理。独立审查需要非实现者；同一代理复查自己的实现只能称为自审。

## 4. 派发与共享资源

每份子任务只携带必要上下文：目标、相关规格与文件、输入/输出、依赖、允许范围、资源 owner、禁止项和验收。以路径和准确的结果摘要引用长记录，不向所有代理复制完整历史、无关源码或凭据。未实际测量的成本、节省比例和速度不编造数字。

- **写入唯一 owner**：同一文件及会修改它的生成器只允许一个 owner；其他代理可读取、反馈或提交建议。变更所有权需协调者明确交接，避免并行覆盖。
- **环境唯一 owner**：每个共享数据库/schema、账号、容器、端口、浏览器会话/配置都指定唯一 owner；其他代理通过 owner 请求操作，或使用协调者分配的独立资源。只读访问也须确认不会争抢登录、会话或触发隐含写入。
- **重型资源限制**：先登记本任务可运行的数据库实例、容器、构建、全量测试和浏览器数量/并行上限。未设定前不得并行启动重型任务；冲突任务排队，能复用的健康资源按所有权复用，不重复启动。
- **统一集成**：共享分支的合并、整体验证和部署由协调者统一组织；代理只在分配范围内交付。提交、推送、合并、tag/Release、部署及真实数据操作仍按当前授权分别判断。
- **不扩权**：子代理不能扩大文件或环境范围、借用其他任务资源，不能自行转委托或更换到超出已指定范围的模型；需要调整时向协调者说明证据和理由。协调者确认现有授权后可在范围内调整，无需重复向用户审批。

启动和清理均核对资源标识、归属及进程状态，只清理本任务明确可释放的资源；保留环境、用户数据和其他任务进程不因“清理”被停止或删除。

## 5. 执行、失败与重评估

沿用小步流程：阅读规格 → 实现 → 实际运行 → 测试 → 修复 → 阶段交付。依赖顺序明确后直接推进，更新任务状态并及时说明新发现、限制和下一步要解决的问题。

失败先分类，再决定动作：

| 类别 | 下一步 |
| --- | --- |
| 规格或验收含糊 | 对照约束与证据，由 Astra 收敛判断；缺少必要用户决定时只询问具体歧义 |
| 实现或测试失败 | 定位根因，提出可验证假设，修复后运行适当检查 |
| 网络、凭据、权限或资源阻塞 | 检查连接、授权和资源归属，使用范围内可行替代；更换模型不能解决此类阻塞 |
| 模型推理难点 | 检查是否遗漏上下文或任务拆分不当，再由 Astra 处理关键判断，或有理由地调整 Sol 强度 |

每次重试记录新的假设、与前次不同的动作及结果，不原样循环。**连续两轮有证据的失败后必须重评估**目标、根因、上下文、任务拆分、环境和模型分配，更新方案或说明阻塞；这不是自动升级模型的触发器，也不是删除失败证据或放弃门禁的理由。当前任务中仍有效的更严格任务/发布重试上限继续生效。

难点解决后，把清晰的实施步骤与验证条件交回 Sol；保留首次失败、修正及最终结果，不能只报告最后一次成功。

## 6. 验证与交付证据

测试按实际风险和影响选择，满足仓库与本任务必需门禁。文档修改通常检查内容、链接和 diff；行为修改覆盖受影响路径、失败/权限/CAS 等相关边界。涉及发布时保留完整既有门禁，不因模型、成本或工期删减。

不得为了通过而弱化断言、跳过真实失败、缩减应有覆盖或把未跑项目记为通过。修正错误夹具/定位必须说明原始失败原因、为何修正合理及重跑结果；条件跳过和环境阻塞分别列出。

交付附上实际执行的命令、结果/退出状态、对应版本或工作区基线及日志/截图路径，并明确证据层级：

- **静态检查**：类型、构建、契约、lint 或文档检查，只证明各自检查范围。
- **Mock/模拟接口验证**：明确模拟接口、内存状态等替代了什么；浏览器打开成功不能推断真实后端或数据库已验证。
- **真实隔离验证**：实际服务/数据库/浏览器主链，标明隔离环境和资源，证明实际走过的操作及结果。可使用合成数据，分别记录数据来源与服务是否真实，不能因数据为合成而称作 Mock。
- **未运行**：列明未跑项、原因及其对验收的影响；不得用解析用例、历史结果或代理报告代替本轮执行。

协调者必须查看实际 diff、相关规格与原始证据，并按风险独立复核关键行为或结果；不只采信子代理“已通过”的结论，也不无理由重复其全部可靠工作。独立审查由非实现者完成并注明审查范围；没有独立审查时写“自审”或“未做独立审查”。

仅在当前目标和必需验收均满足、无未解释的关键失败时标记完成。否则交付已完成部分、缺口和阻塞，准确说明可交付程度。

## 7. 追加需求、暂停与恢复

追加需求先由协调者更新任务表、范围、验收和依赖，保留原目标及已经完成的有效工作；只有用户明确取消或新目标确实不兼容时才替换原目标。已授权且互不依赖的工作继续推进。

暂停或调整代理前通知停止新操作，并核对当前命令和副作用。不能把“已发中断”当作“所有操作已停止”；长任务、迁移或环境切换按自身安全边界处置，不强制终止到不一致状态。记录未完成命令、已发生写入、资源归属及后续恢复动作。

恢复时先核对 `git status` / diff、基线变化、仍在运行的进程/测试、环境资源和上次动作是否已完成；核对当前有效授权及范围变化后，从未完成步骤继续，无需重新取得同一有效授权。不要重复提交、业务写入、迁移、建库、启动容器或部署。原代理与新 owner 不得同时恢复同一项操作。

## 8. 精简交付与交接模板

```markdown
任务 / 状态：T… / 待验收、完成、阻塞或取消
结果：目标行为或产物；与验收条件逐项对应
改动：文件路径；实际模型/强度（已知时）；关键决定及理由
验证：命令 → 实际结果/退出状态 → 证据路径；注明静态/Mock/真实隔离
未跑 / 失败与修正 / 剩余问题：……（无则写“无”）
审查：自审或独立审查；审查人/代理、范围、结果与证据
资源与副作用：owner、进程/端口/容器/数据库/账号/浏览器状态；已发生写入
下一步 / 接手条件：依赖、基线与资源核对、未完成命令；避免重复操作的说明
授权边界：已执行的敏感动作及其依据；后续尚未授权的操作
```

简单任务可将模板压缩为几句话，但保留结果、实际验证和重要限制；有并行、失败、资源占用或交接时补齐相应信息。
