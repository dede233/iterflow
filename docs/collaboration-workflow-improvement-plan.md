# 迭程 IterFlow 协作流程优化方案与实施计划

日期：2026-10-31（Asia/Shanghai）
状态：2026-10-31 用户授权开工，按推荐默认值分阶段实施
目标版本：下一功能版本，版本号在实施范围冻结时确定

本次优化围绕实际使用中的五类问题：反馈填写冗余、接收责任不清、缺少邮件进度通知、需求流转繁琐且不直观、版本关联需求操作效率低。目标是让提交人少填写、参与人知道当前待办，并让处理过程可追溯。

用户已确认：反馈通知多人、单人确认；需求取消独立排期流转；需求取消总负责人，采用确认、设计、开发、验收人员分工。本方案将这些决定展开为流程、通知、兼容与实施要求。未逐条讨论的边界规则归入“实施建议”，不冒充既有规则或已批准实现。

## 1 范围与授权边界

### 1.1 已确定的产品方向

| 范围 | 目标行为 |
| --- | --- |
| 反馈表单 | 移除期望结果、实际结果输入项；保留历史内容 |
| 反馈接收 | 支持一位或多位接收人，通知多人，一人确认受理即可 |
| 邮件通知 | 关键进度和待办可通过邮箱送达，保留站内通知 |
| 需求流程 | 待确认 → 待开发 → 开发中 → 待验收 → 待发布 → 已上线 |
| 需求人员 | 无总负责人；按确认、设计、开发、验收环节分工 |
| 进度展示 | 纵向进度区展示当前阶段、人员、确认结果、时间和下一步操作 |
| 设计工作 | 可选；设计人员与进度在需求内展示，不增加强制设计审批节点 |
| 版本添加需求 | 多选、搜索、筛选、跨页保留选择 |
| 版本查看需求 | 原地打开摘要弹窗，保留完整详情入口 |

### 1.2 保留的工程和业务约束

- Feedback → Requirement → Version → Publish → Release 主链不变，反馈不能直接成为版本项。
- 一条反馈最多一个主需求；多条反馈可以关联同一需求；需求同时最多有一个有效版本关系。
- 版本发布仍由专用事务完成；Release 仍表示实际成功发布；需求与反馈上线仍只能由发布事务产生。
- 状态、人员、确认、关系修改必须校验 revision；冲突返回 409，不能静默覆盖。
- RBAC、DataScope、审计、StorageService、同一 Vue 工程响应式适配继续有效。
- 不引入工时、Story Point、通用流程设计器、多人会签、邮件回复审批或第二套移动端项目。
- “取消总负责人”仅针对 Requirement；Version 的负责人不在本次删除范围。

2026-10-31 用户在审阅本方案后授权开工，按本方案推荐默认值实施。AGENTS.md 已补充本轮授权，替代历史版本对本轮增量范围的限制；开发契约和状态规格随相应能力先行更新。已发布契约、标签、Release、历史审计不得重写；实际环境迁移、正式合并及部署不在开工动作中执行。

## 2 当前实现与变更影响

以下事实来自当前本地源码，不能据此推断运行环境已经采用某个 commit。

| 当前实现 | 本次需要处理的影响 |
| --- | --- |
| 反馈有 expected_result、actual_result 可空字段 | 移除新表单输入，不删除旧内容；普通编辑不能用 null 清空历史内容 |
| Feedback SELF 范围仅按 submitter_id 判断 | 新增接收人不能仅发送通知，必须校验接收人能否查看、能否受理 |
| Requirement SELF 范围按 created_by 或 owner_id 判断 | 取消 owner 必须同步调整参与人访问规则并兼容旧访问范围 |
| 需求有 DRAFT、CONFIRMED、PLANNED 等状态 | 合并确认与排期后的阶段；更新查询、统计、按钮、状态策略和测试 |
| Feedback 转新 Requirement 时自动设为 CONFIRMED | 不能据此伪造指定确认人的确认事实；需要定义新转换语义 |
| 加入版本会把 DRAFT／CONFIRMED 变成 PLANNED | 新方案中关联版本与人员确认解耦，不能借批量添加跳过确认 |
| 用户资料有 email，业务通知主要在发布时创建 | 需补通知事件、邮件发送任务、偏好、重试和可观察性 |
| 版本添加需求一次仅处理一条，查看会导航到需求页 | 需批量事务与摘要弹窗，继续执行对象级权限校验 |

主要依据见文末“源码与规格索引”。

## 3 反馈流程

### 3.1 提交与编辑

保留标题、类型、描述、现有业务系统／模块、紧急程度、附件等已有内容，新增接收人多选。仅移除期望结果和实际结果输入项；复现步骤不在本次删除范围，可作为按需填写的补充信息。

实施建议：新提交必须选至少一位有效接收人；历史反馈允许接收人为空，显示“历史反馈，待补充分工”，不因普通编辑强制补填。接收人选择提供搜索、已选标签、去重和清除能力。

候选人员只返回完成选择所需的最小信息，如用户 ID、显示名和可接收资格，不直接开放整个用户管理目录或邮箱列表。候选查询和提交必须同时检查有效账号与资格，不能依赖前端选项。

### 3.2 多人通知与单人受理

正常路径为：提交 NEW → 一人确认受理 ACCEPTED → 转为或关联需求 REQUIREMENT_LINKED → 发布后 ONLINE。

| 动作 | 执行规则 | 结果 |
| --- | --- | --- |
| 提交 | 保存反馈、接收人和通知事件，同一事务提交 | 所有有效接收人收到新反馈提醒 |
| 确认受理 | 任一有受理权限和对象访问权的接收人执行 | 记录受理人、受理时间；默认由此人负责反馈处理 |
| 并发受理 | 同一反馈 revision 仅允许一个请求成功 | 后到请求返回 409，并显示已由谁受理 |
| 转交处理 | 有管理权限的人选择有效接收人并填写原因 | 更新当前处理人，保留最初受理事实，通知新旧处理人 |
| 增减接收人 | 提交人或有反馈编辑权限者在可编辑范围内操作，校验 revision | 新增人员收到一次提醒；移除人员不再收到后续关注通知 |
| 转需求 | 延续现有原子事务、权限和主需求唯一约束 | 反馈保留自身状态，不复制需求研发状态机 |

“单人确认”表示一人即可完成受理，不代表通知只发给一人。其他接收人作为关注人员，无需重复确认。站内已读、邮件发送成功、受理确认是三种不同事实。

实施建议：当前处理人不能直接从接收人中移除，须先完成转交；管理员代受理或代转交必须满足权限并记录原因，不能把实际操作者记成指定人员。账号被停用时保留历史姓名和操作记录，提示重新分配，不自动把责任转给管理员。

重复、无法复现、关闭和重开继续遵循既有反馈状态规则。重开创建新的受理轮次，保留原受理历史；旧处理人可保留为候选接收人，但不能自动显示本轮已受理。

### 3.3 接收人的访问范围

第一版建议采用此前提出的最小范围：只允许选择已经具有该反馈读取资格的人员，受理按钮还需要现有反馈状态操作权限。选择接收人本身不自动赋予角色或全局权限。

这一规则的实际限制是：目前只有 SELF 范围、且不是提交人的账号不能接收别人的反馈。候选为空时必须明确提示由管理员配置有资格的接收人，不能静默改为全员可见。

如果实际团队希望 SELF 用户也能接收别人指定的反馈，应在阶段 0 明确选择“接收人参与关系扩展本条反馈可见性”。这是额外的数据范围规则，需覆盖详情、列表、附件、评论和通知，不能只改一个 GET 接口。本方案不默认扩大反馈可见性。

## 4 需求流程与人员分工

### 4.1 六个主阶段

| 阶段 | 展示与待办 | 正常退出条件 | 下一阶段 |
| --- | --- | --- | --- |
| 待确认 | 确认人、需求内容、验收标准、待确认标记 | 指定确认人确认范围与验收标准 | 待开发 |
| 待开发 | 开发人员、可选设计人员、版本归属、设计进度 | 已分配至少一名开发人员，由有权限的开发人员开始开发 | 开发中 |
| 开发中 | 开发人员、设计完成情况、验收人 | 已指定验收人，提交验收；启用设计时须完成设计或明确取消设计要求并留痕 | 待验收 |
| 待验收 | 指定验收人、提交时间、本轮验收结果 | 验收通过；不通过则填写原因退回开发 | 待发布／开发中 |
| 待发布 | 验收通过信息、关联版本、等待发布说明 | 所属版本成功发布且满足现有发布规则 | 已上线 |
| 已上线 | 实际发布时间、版本、Release 链接 | 终态，不提供人工上线按钮 | 无 |

实施建议：保留现有技术状态码中可复用的 DRAFT、CONFIRMED、DEVELOPING、TESTING、DONE、ONLINE，分别对应上述六阶段；PLANNED 退出新工作流。界面“待验收”仍承担原测试与验收职责，“待发布”仍对应 DONE，不改变发布事务对完成需求的判定。

不以关联版本作为“已确认”的证据。需求可以先确认或开发、再加入版本；若无版本，待发布区明确提示“尚未关联版本，无法发布”。版本关系调整不再自动改变需求阶段。正式发布仍检查该版本全部有效需求，不能只检查当前用户可见清单。

### 4.2 人员模型

| 人员角色 | 数量 | 必须分配的时点 | 职责与操作 |
| --- | --- | --- | --- |
| 需求确认人 | 一人 | 执行确认前 | 确认需求范围、验收标准；记录实际确认结果 |
| 设计人员 | 零到多人 | 启用设计并开始设计前 | 维护设计内容及设计进度 |
| 开发人员 | 一到多人 | 开始开发前 | 开发、提交验收、处理退回 |
| 验收人员 | 一人 | 提交验收前 | 验收通过或退回 |

同一用户可承担多个环节。多人设计或开发不自动形成会签：实施建议由任一有权限的本环节人员提交环节完成，记录实际操作者，对外展示该环节整体进度；第一版不做每人完成百分比或逐人强制打勾。

需求没有总负责人字段输入、总负责人筛选和总负责人兜底操作。列表改为“当前待处理人”，人员筛选采用参与人及环节角色；设计与开发并行时可展示两组待办。未分配显示“待分配”。2026-10-31 用户调整：反馈转新需求时，需求确认人默认当前登录账号，可以更换或清空；当前账号缺少需求读取资格时保持待分配，沿用服务端人员资格校验。直接新建需求及其他环节不自动分配创建人。

人员调整与阶段动作分离：分配人员不代表对方已经确认；完成操作记录操作者、时间、结果、当时人员配置及 revision。更换尚未开始环节的人员仅更新待办；更换已完成环节的人员不改写历史确认人。

### 4.3 设计子进度

设计为可选工作，子进度采用“不需要设计／未开始／进行中／已完成”。它不改变六阶段主链，也不单独产生上线资格。

设计可在待开发开始，并可与开发并行。启用设计时在提交验收前完成；取消设计要求需要原因和审计。设计退回或需求范围变化时，可重新打开设计工作，旧完成记录保留，不能把历史完成时间覆盖成最新时间。

### 4.4 退回 暂停 取消与内容变化

| 场景 | 实施建议 |
| --- | --- |
| 确认人要求补充 | 保持待确认，记录意见，不新增审批状态 |
| 验收不通过 | 待验收 → 开发中，原因必填；下一次提交产生新验收轮次 |
| 待发布重新开发 | 沿用 DONE → DEVELOPING 的限制：所属版本未发布、原因必填、审计完整 |
| 暂停 | 待开发、开发中、待验收可暂停；保存暂停前阶段，界面显示暂停原因与恢复目标 |
| 恢复 | 保留现有允许的恢复目标，按新状态映射为待开发或开发中；原来处于待验收也需重新提验，不增加直接恢复验收的新通道 |
| 取消 | 保留原边界：待确认、待开发或已暂停可取消；开发中／待验收先按规则暂停，不增加直接取消通道 |
| 已上线或已取消 | 保留终态，变更需求按既有后续业务流程处理，不新增重开入口 |
| 已确认后修改范围或验收标准 | 保留旧确认所对应的内容快照，标记“内容已变更，待重新确认”；由确认人确认当前内容后才能继续下一正向流转或发布 |

最后一项属于实施建议：新需求的确认结果应绑定内容版本，不能让旧确认代表新内容。标题错字、人员调整等非范围修改不自动失效确认；影响范围的字段清单在阶段 0 固定。历史需求采用第 8 节的兼容规则，不凭空追补过去的确认。

### 4.5 反馈转换与直接创建

推荐统一语义：直接创建和反馈转新需求均从待确认开始；反馈已受理不等于需求范围已由确认人确认。转换页面可一次指定确认、设计、开发、验收人员，允许尚未到达环节暂不分配。

为减少重复点击，可以提供明确标注的“创建并确认”：仅当操作者就是指定确认人、具备相应权限且资料完整时可用；创建、确认记录、反馈关系、状态、审计及通知事件在同一事务完成。普通“转需求”不能隐式执行确认，也不能自动赋予转换人需求状态权限。

关联已有需求不改变该需求的确认记录和当前阶段。来源反馈和需求相互导航仍分别校验各自权限。

### 4.6 操作资格与数据范围

业务上的“确认人、开发人员”等是本需求的参与关系，不是新的系统角色。执行动作需要同时满足：已登录、现有对应权限码、对象数据范围、当前环节资格及 revision 校验。普通状态更新入口必须走相同规则，不能绕开确认或验收记录。

建议保留现有 rd.requirement.edit 用于分配人员，rd.requirement.status 用于状态动作；参与关系本身不授予权限码。管理员代操作必须有明确的现有管理员资格、相应权限与原因，审计同时保存指定人员与实际操作者。其他具备全局数据范围的人也不能冒充指定人员确认。

取消总负责人后，Requirement SELF 读取范围建议调整为“创建人或有效环节参与人或明确保留的历史访问成员”；ALL 仍按既有规则。旧负责人保留的是历史读取兼容，不因此获得任何新环节动作资格。移除参与人后，若无其他可见依据，则后续读取与通知停止。

参与某需求不自动获得所属版本、来源反馈、其他需求或整个用户目录的读取权限。列表、total、统计、弹窗、关系选择、附件与通知必须使用一致的数据范围。

## 5 进度区与版本工作区

### 5.1 需求进度区

2026-10-31 用户调整：进度区放在详情上方，默认收起为紧凑摘要，显示当前阶段、对应环节人员（或版本信息）、内容待确认提示。点击整行或使用键盘可展开、收起。展开后桌面端横向展示六阶段，平板三列、手机两列；人员设置和历史记录可单独展开。切换需求或账号时恢复收起，同一需求刷新 revision 时保留展开状态。完成、当前、未开始、暂停不能仅靠颜色区分；确认和流转仍需显式操作。

阶段信息示意（展开后按上述响应式布局展示）：

```text
✓ 需求确认    王某 已确认 10月28日 14:30
✓ 待开发      开发人员已分配
● 开发中      李某、赵某
  设计：陈某 已完成
  验收人：张某
  下一步：提交验收
○ 待验收      尚未提交
○ 待发布      所属版本：下一迭代
○ 已上线      等待实际发布
```

“已确认”来自真实业务记录，未来节点不能提前显示完成时间。退回后主进度回到当前阶段，历史验收结果在历史记录中保留。暂停时展示“暂停于哪个阶段”，不能把之后的节点画成已完成。

节点内提供人员配置、查看确认意见和当前允许动作；无权限时只读。PC、平板和手机使用同一信息结构，小屏改单列，操作不依赖悬停。弹窗打开和关闭应支持键盘焦点返回与可读标签。

### 5.2 批量添加需求

- 弹窗支持编号／标题搜索、状态／优先级筛选、多选、跨页保留勾选和已选数量；“全选”明确仅为当前页，不暗示选中所有搜索结果。
- 已在本版本的需求禁选并说明原因；已有其他有效版本归属的需求提示走迁移，不自动迁移。
- 推荐首版单次最多 50 条，可在性能验证后调整；仅为实施建议，不是当前限制。
- 提交携带版本 revision 和每条需求选择时确认的 revision，服务端逐项校验权限、归属、状态和并发。
- 采用全成全败事务：任一项无效或冲突，全部不添加，返回用户有权查看的逐项原因，保留选择便于修正。
- 成功后每条需求更新一次 revision，目标版本作为本次批量操作更新一次 revision；分别记录关系审计。一次批量操作只提交一次事务，不循环调用会单独提交的旧接口。
- 重复提交通过请求标识和 revision 防护避免重复关系、重复审计或重复通知；不得自动刷新 revision 后重放写请求。
- READY／RELEASED／CANCELED 等既有冻结边界继续生效；添加行为不改变需求确认阶段。

### 5.3 需求摘要弹窗

版本内“查看”打开摘要，包含编号、标题、类型、优先级、主阶段、当前待处理人、各环节人员、描述、验收标准和可见来源反馈。2026-10-31 用户调整：需求摘要不显示需求进度区域，进度在完整需求详情查看。默认以只读摘要为主，不把完整编辑页和全部操作堆入弹窗。

保留“打开完整详情”；关闭后保留版本筛选、分页与滚动位置。移动端采用全屏弹层。读取需求本身仍调用受保护接口，不能把父版本可见性当成所有子需求可见性。对 403／404／网络错误提供局部提示，不影响版本详情；切换对象、关闭弹窗和切换账号后丢弃旧响应。

## 6 通知规则

### 6.1 通知对象与渠道矩阵

下表为目标规则。待办与结果通知默认生成站内通知；邮件是否发送还受个人偏好、邮箱有效性和发送时访问权限限制。同一事件、同一用户、同一渠道只生成一份通知。

| 事件 | 主要接收对象 | 邮件类别 |
| --- | --- | --- |
| 新反馈提交 | 全部反馈接收人 | 待办 |
| 新增反馈接收人 | 本次新增人员 | 待办／关注 |
| 确认受理 | 提交人、其余接收人 | 关键进度 |
| 反馈转交 | 新旧处理人；提交人和接收人收到负责人变化 | 待办／关键进度 |
| 反馈关闭、无法复现、重复或重开 | 提交人、有效接收人、当前处理人 | 关键进度 |
| 转为或关联需求 | 反馈提交人、接收人；新需求确认人另收待确认通知 | 关键进度／待办 |
| 需求请求确认或要求重新确认 | 指定确认人 | 待办 |
| 需求确认或要求补充 | 创建人、开发人员；需补充时通知创建人 | 关键进度／待办 |
| 分配或调整环节人员 | 新旧相关人员 | 待办／分工变化 |
| 开始开发 | 需求参与人、关联反馈关注者 | 关键进度 |
| 提交验收 | 验收人；参与人和关联反馈关注者接收进度 | 待办／关键进度 |
| 验收退回 | 开发人员；确认人及其他有关参与人 | 待办／关键进度 |
| 验收通过 | 需求参与人；有权限的关联版本负责人收到待发布提醒 | 关键进度／待办 |
| 需求暂停、取消或恢复 | 需求参与人、创建人、关联反馈关注者 | 关键进度 |
| 版本关联或迁移变化 | 有权查看的需求参与人和相关版本负责人 | 关键进度 |
| 实际上线 | 需求参与人、创建人、关联反馈提交人及有效接收人 | 上线结果 |

“关联反馈关注者”指该反馈提交人和当前有效接收人。对只拥有反馈读取权的人，只发送基于该反馈的进度摘要并链接反馈详情，不暴露需求描述、内部人员意见、其他来源反馈或无权读取的版本信息。

普通字段编辑、打开页面、标记已读不发送进度邮件。设计子进度的日常调整默认不发给所有反馈关注者；只有产生明确待办或阻塞时通知相关设计／开发人员。

实施建议：主动操作者不再收到同事件的重复提醒，但审计仍保留；同一用户兼任多个角色或提交多条关联反馈时按事件聚合，避免同次发布重复轰炸。移除人员的分工变更提醒只含中性信息，不携带其已失去读取权限的对象内容。

### 6.2 邮件内容与个人设置

邮件主题建议为“迭程 IterFlow｜编号｜进度变化”，正文包含最小必要的标题、前后进度、发生时间与站内链接。无权限内容不得进入模板；默认不附完整描述、附件、内部意见或可长期匿名访问的链接。链接使用可信配置的站点地址，打开后正常登录并校验权限，不携带 Access／Refresh Token。

个人设置提供“全部关键通知”“仅待办与上线”“关闭邮件”。建议默认“仅待办与上线”；站内通知独立保留。旧用户的邮件开关在启用时明确告知，正式启用前确认邮箱归属，不对历史事件补发。

邮箱为空、格式无效或尚未确认归属时，保留站内通知，展示配置提示。邮箱修改后的验证、旧地址待发任务的处理和发送身份配置在邮件阶段实现。邮件送达状态不作为人员确认或已读依据。

### 6.3 可靠发送与运维

业务事务内保存通知事件／待发送记录，提交后由后台 worker 发送。数据库中的任务记录是持久依据，Redis 可用于调度，不能仅依赖进程内后台任务或 Redis 临时消息保证送达。

- 事件记录与业务变化一起提交，事务回滚不得残留通知；SMTP 失败不回滚已成功的反馈、确认或发布。
- 任务保存事件 ID、收件用户、渠道、状态、尝试次数、下次重试时间和脱敏错误；唯一键防止重复创建任务。
- 发送前重新检查账号、邮箱、偏好和对象读取资格；失去资格标记跳过，不把旧正文发送给已无权用户。
- 瞬时错误采用有上限的退避重试；永久错误停止自动重试并记录。手动重试仅针对失败任务并受管理权限控制。
- SMTP 超时可能发生“服务端已接收但应用未获响应”，不能声称邮件严格只送达一次。使用稳定 Message-ID 和投递记录减少重复，并在重试设计中处理结果不确定状态。
- 邮件正文做 HTML 转义，SMTP 凭据由部署配置保管；日志不记录密钥、令牌或完整敏感正文。
- 测试与预览环境默认使用测试收件箱或白名单，不向真实人员自动发送测试邮件。正式 SMTP 连通性测试与实际发送另按实施阶段授权执行。

## 7 数据与接口设计建议

以下为逻辑设计，准确表名、字段、路径和错误码在 contract-first 阶段确定。保持现有技术栈，不增设新的核心业务实体。

| 数据范围 | 建议新增或调整 | 必须保持的约束 |
| --- | --- | --- |
| 反馈接收关系 | feedback_id、user_id、加入／移除信息 | 同一反馈有效接收关系唯一；不物理抹去处理历史 |
| 反馈受理 | 当前处理人、受理轮次、实际受理人和时间 | 一轮只能成功受理一次；转交不改写原受理事实 |
| 需求参与关系 | requirement_id、环节角色、user_id、有效标记 | 确认人与验收人各最多一位有效人员；设计／开发可多人 |
| 阶段记录 | 轮次、动作、实际操作者、内容版本、时间、结果、意见 | 确认事实与状态变更同事务；旧记录不可覆盖 |
| 设计子进度 | 是否启用、进度、完成记录 | 与主阶段区分；无需设计不构造完成事实 |
| 历史读取兼容 | 原 owner 与历史对象的读取依据 | 不冒充环节分工，不授予状态操作资格 |
| 通知与投递 | 业务事件、收件记录、重试状态、偏好 | 唯一事件键、提交后发送、发送前重新鉴权 |

接口能力至少包括：最小人员候选查询、反馈接收人修改／受理／转交、需求人员分配、确认与验收动作、设计进度、需求进度读取、批量关联需求、本人邮件偏好和邮箱验证。摘要弹窗优先复用现有详情读取，只有投影确实不足时才增加接口。

实施顺序为修改 spec/openapi-development.yaml → 生成前端类型 → 后端实现 → 前端实现 → parity 校验。继续保持 401 未登录、403 无操作权限、404 对象不可见或不存在、409 并发或非法流转、422 输入不合法的既有边界；具体错误码沿用项目规范。

所有参与人、受理、确认、验收、设计进度修改以所属 Feedback／Requirement 的 revision 为并发边界，成功递增并写审计。批量关联同时保护版本与每条需求。新增支撑表通过 Alembic 管理，不能只在真实数据库手工加列。

## 8 旧数据与旧客户端兼容

### 8.1 状态映射

| 旧状态 | 新展示 | 数据处理建议 |
| --- | --- | --- |
| DRAFT | 待确认 | 保留状态；缺失人员显示待分配 |
| CONFIRMED | 待开发 | 保留状态码；标记历史确认，人员／时间仅在可信证据存在时展示 |
| PLANNED | 待开发 | 迁移为 CONFIRMED；单独保留原状态映射记录 |
| DEVELOPING | 开发中 | 保留状态；不推断开发人员 |
| TESTING | 待验收 | 保留状态；进入新验收动作前分配验收人 |
| DONE | 待发布 | 保留已完成资格，不强制历史需求重新验收 |
| ONLINE | 已上线 | 保留历史终态和真实发布关联 |
| PAUSED | 已暂停 | 保留；暂停前阶段有可信审计则恢复展示，否则标记历史阶段未知 |
| CANCELED | 已取消 | 保留终态 |

迁移不触发进度邮件、不生成伪造确认或验收、不重新发布版本。ID、编号、反馈关系、有效版本关系、Release、附件和历史审计保持一致。状态变化的行按迁移方案递增 revision，使旧页面写入能够被识别为过期。

### 8.2 历史字段与人员

- expected_result、actual_result 暂保留数据库和兼容读取；新页面仅在有内容时显示“历史补充信息”。更新其他字段不发送这两个字段，不能将它们自动覆盖为空。
- 原 owner_id 保留为历史信息和读取兼容依据，不自动转换为确认人、设计人员、开发人员或验收人。新需求不再填写 owner。
- 历史反馈没有接收人或受理人时，显示历史未知／待分配；不能把 updated_by 或创建人当作受理人。
- 仅当历史审计能明确证明具体动作、操作者、时间时才用于历史展示，并标记来源；否则保留未知。
- 已完成和已上线历史需求采用历史完成兼容标记，不因新增人员字段为空而失去原有发布或查看资格。若重新开发，后续动作按新流程补齐人员和新轮次记录。
- 尚在进行的历史需求不强制倒退阶段；在下一次需要人员确认的动作前完成必要分配。旧人员停用或不存在时保留历史显示，不选择新账号替代。

### 8.3 旧接口与客户端

历史发布契约文件保持不可变，但新服务的工作流行为确实发生变化，不能宣称与所有旧写入客户端完全兼容。

建议采用受控切换：新 API 保留可空历史字段用于读取，旧 owner 写入和 PLANNED 写入在切换后明确拒绝并提示刷新／升级；不能静默忽略 owner 写入或把 PLANNED 自动解释成某人的确认。旧查询条件可在过渡期将 PLANNED 映射到待开发并标记废弃，owner 筛选仅解释为历史 owner 筛选，不偷偷改成所有参与人。

切换前盘点旧前端缓存、脚本和外部调用方；如确有长期旧写客户端，阶段 0 应选择显式版本化的兼容适配方案，而非混用两套确认规则。新前后端和 worker 必须按兼容顺序上线，刷新页面后才能继续新写操作。

### 8.4 迁移与回退

1. 先增加可空列和支撑表，不删除旧字段；在一次性测试数据库验证迁移和约束。
2. 对旧状态、owner、版本关系、发布记录、孤立引用和人员有效性做只读盘点，形成迁移前清单。
3. 在隔离的代表性旧数据副本演练状态映射、历史访问兼容与新旧读写切换；迁移应可重复验证，不重复生成映射记录。
4. 切换时暂停写入和通知消费，执行正式迁移后核对各状态数量、关系完整性、历史读取范围及 revision，再启用新服务。
5. 先验证站内通知，再启用邮件投递；迁移期间不补发历史事件。
6. 回退不等于直接把旧应用连接新数据：新分工、确认轮次和投递记录无法无损还原为一个 owner。发生故障先停写和暂停发送，按已演练的回退方案处理；优先保留数据并前向修复。

正式环境备份、恢复、数据迁移与部署属于后续独立执行步骤；本轮不执行。若确需恢复备份，必须处理切换后的新增数据及已发送邮件无法撤回的事实，不能用破坏性降级掩盖数据丢失。

| A03 | 并发受理 | 两人同时确认只有一个成功；另一方 409；负责人和审计一致 |
| A04 | 受理转交与重开 | 原确认事实不覆盖，重开产生新轮次；无重复待办 |
| A05 | 取消总负责人 | 新页面和新写入无总负责人依赖；分环节人员可管理 |
| A06 | 六阶段主链 | 确认后直接待开发，无单独排期点击；节点能解释当前待谁处理 |
| A07 | 人员与资格 | 未分配不能执行对应动作；非指定人不能冒名确认；多角色兼任可用 |
| A08 | 设计与验收 | 无设计任务可正常完成；设计多人不强制会签；验收退回保留历史 |
| A09 | 转换与关联 | 转反馈不伪造确认；加入版本不改变确认阶段；关联已有需求不覆盖其记录 |
| A10 | 状态与 revision 绕过 | 直接调用普通状态／编辑接口不能绕过节点规则；旧 revision 均 409 |
| A11 | 批量关联成功与失败 | 成功全部加入；任一对象无权、冲突或冻结则全部不加入；关系和版本 revision 正确 |
| A12 | 批量并发 | 与移入／移出／迁移／发布竞争时无重复有效关系、无部分提交 |
| A13 | 摘要弹窗 | 权限隔离、关闭回位、旧响应丢弃、移动端可用 |
| A14 | 通知一致性 | 事件随业务回滚，重复请求不生成重复站内通知；邮件错误不影响业务成功 |
| A15 | 邮件失败恢复 | worker 重启、SMTP 超时、退避重试、永久失败可识别；不声称严格一次投递 |
| A16 | 邮件隐私 | 权限撤销、人员移除、邮箱变更后不会发送越权内容；无 Token 或密钥泄漏 |
| A17 | 旧数据 | PLANNED 正确映射，旧 owner 历史读取兼容，缺失确认人不伪造，旧 DONE 不被新增字段阻断 |
| A18 | 完整发布 | 版本 READY 后正式发布，生成一条 SUCCESS Release，符合条件的需求和反馈上线，提交人收到通知 |
| A19 | 发布事务故障 | 任意关键写点失败时 Release、状态、关系要求及通知事件保持原子性；无先发邮件 |
| A20 | 响应式与权限 | 375／390／768／1280／1440 视口；至少 SELF 与 ALL、无对应权限、停用账号、切换账号场景通过 |
| A21 | 基础回归 | Auth 登录／刷新／失效、RBAC、附件、审计、PostgreSQL 约束、Docker 健康检查及契约类型一致 |

实施时运行与改动相符的后端测试、真实 PostgreSQL 并发与迁移测试、前端组件测试、Playwright、类型生成和 OpenAPI parity。发布候选继续执行现有六项 CI：backend、frontend、docker_smoke、s3、browser_smoke、backup_restore。备份恢复门禁仅在隔离一次性环境执行，不能把它当成真实环境恢复授权。

## 12 实施前需定稿的细则

产品主方向已确定。下列事项是本次为形成完整方案补充的建议，可在阶段 0 一并定稿，不要求重新确认已同意的六阶段或取消总负责人。

| 事项 | 本方案推荐默认值 |
| --- | --- |
| 反馈候选人的数据范围 | 先只选已有读取资格的人员；如实际需要 SELF 接收别人反馈，显式批准本条反馈参与范围扩展 |
| 新反馈接收人必填 | 至少一人；历史反馈兼容空值 |
| 转新需求的确认语义 | 默认待确认；符合资格时可显式创建并确认 |
| 多人开发或设计的完成方式 | 任一本环节有权限人员代表环节提交，保留操作者；不设逐人会签 |
| 设计是否阻塞提验 | 启用设计后须完成或有原因取消要求；不阻塞开始开发 |
| 范围变化后的确认 | 新需求按内容版本重新确认；历史完成需求按兼容政策处理 |
| 暂停与退回 | 保持既有合法目标，原因必填，保留每轮历史 |
| 邮件偏好 | 默认仅待办与上线，启用时告知并确认邮箱归属 |
| 批量规模与语义 | 首版最多 50 条，全成全败 |
| 旧写客户端 | 受控切换并明确拒绝废弃写入；有长期集成则设计显式兼容层 |

实施前还需核实实际使用账号的权限分布、现存状态数量、外部 API 调用方，以及可用 SMTP 服务、发件身份和站点地址。这些是环境事实，不能通过方案推断；本轮不读取真实业务数据、不索取或记录邮箱密钥。
