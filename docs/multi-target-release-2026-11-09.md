# 多目标发布实施与验证（2026-11-09）

## 授权和范围

用户要求完成既有多小程序方案。基线 5d79a48，独立本地分支 codex/multi-target-release；不部署、推送、合并或访问真实数据库。必要追加迁移仅在本任务新建隔离 PG/MySQL standard/portable 验证。原准备候选及双远端 master 保留，原八项 CI 不冒用为本增量验证。

## 确定实现

- 业务系统维护发布目标（PC Web/微信小程序、编码/名称、可选 AppID/访问地址、启停），有引用只停用不删除，不跨系统改属；使用原系统管理权限与 ALL 范围。
- 版本保留单系统与原 Release 一对一主链。增加 INITIAL 首次、SUPPLEMENT 补发、REPUBLISH 显式重新发布三种批次，每批最多50个同系统目标并保存当时名称/平台/编码/AppID/地址快照。
- 先做现有发布检查再建首次计划；登记实际成功记录后冻结需求清单、需求写入及归属，主阶段仍 READY。最后一个实际成功在同一事务内复用 Version 发布事务，生成唯一 Release 并同步需求/反馈/通知/审计；失败整笔回滚。
- 已上线版本可补发尚未覆盖的目标；再次覆盖已发布目标必须明确创建 REPUBLISH 批次并填写原因。原 Release、首次时间、需求 ONLINE 和全局上线通知不改变。实际时间与系统登记时间分开，重复/旧 revision 不重复登记。
- 目标尚未完成时可带原因调整批次计划；完成行不可移除或改写。若调整后首次计划全完成，需明确执行整体发布确认，计划修改本身不静默触发上线。首次已有成功不能取消整个批次；后续批次可取消未完成部分，成功记录与累计覆盖保留。
- 历史 Release 显示“历史发布，未记录目标”；已发布且无系统归属的历史版本在首次补发时显式选择本次所属系统，保存在批次，不改旧版本/需求/Release，后续保持同一系统。
- 未配置目标且没有首次批次时，旧单次发布接口保持兼容；UI 明确选择传统单次发布。系统已有目标时，传统路径须显式选择并说明原因；任何活动首次计划都不能被传统发布绕过。
- 目标成功表示人工登记外部已完成的发布，不接入平台自动发版、不存 AppSecret；可填写说明和凭证文本/链接，不在后端抓取外部链接。
- 版本详情显示首次/补发进度、累计覆盖及每批历史；发布记录增加目标实际记录和目标筛选，保留原整体发布记录。沿用版本/发布查看权限和 DataScope，目标名称不通过筛选接口泄露范围外对象。

## 事务与兼容约束

统一版本→批次→目标（ID顺序）→需求锁序。批次写入同时校验并增加版本和批次 revision，单个目标完成还校验其 revision；首次收尾只有一次整体 Release/状态同步/全局通知。目录与所有写动作都有审计，不自动重放未知结果。

追加三张表及 Version.release_frozen，旧行默认 false，不回填目标/批次。MySQL 三表完整性/领域触发器、完成记录保护和冻结保护配套；最小运行授权及预检同步，降级遇到目标/批次历史或冻结标记拒绝有损处理。
