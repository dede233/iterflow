# 多目标发布与补发批次方案（2026-11-05）

## 已确认规则

一个版本继续归属一个业务系统，只关联同系统需求。用户确认：首次发布时选择的目标全部完成，才算版本及需求已上线；隔一段时间可将同一版本发布到其他小程序。

建议用“业务系统 → 发布目标；版本 → 发布批次 → 目标实际发布记录”表达。发布目标可表示具体 PC 站点或小程序，不为每个小程序重复建立同一业务系统/需求/版本。本文件为方案，尚未实现多目标发布或修改现有 Publish/Release。

## 目标目录

在业务系统详情维护发布目标：名称、平台类型（PC Web/微信小程序，其他平台按需增加）、目标编码、可选 AppID/访问地址、启用状态。AppID 仅用于识别，不存 AppSecret、发布凭据或接入微信自动发版。目标属于一个系统；有历史引用后停用而不删除，不允许改属另一系统。

版本不固定只属于 PC 或小程序：同一系统如确实共享同一版本，可选多个目标；完全独立的产品/需求应继续独立业务系统。发布选择器只提供当前系统启用目标。

## 首次批次

发布检查通过后，选择本次计划上线目标，如 A、B；明确记录为首次发布计划，保存当时名称/平台/标识快照。每次实际完成一个目标，登记实际上线时间、操作人、说明和可选凭证；这一步表示人工记录已在外部完成的发布，不自动执行平台发布。

A 完成、B 未完成时，详情显示“首次发布进行中 · 1/2”，版本/需求暂不整体标记上线。全部目标成功后，通过专用发布事务一次性生成原主链 Release 并同步 Version/Requirement/Feedback 与通知。不能通过普通状态接口绕过，不把首次单目标成功误报为整体上线。

首次开始实际发布后冻结版本需求清单、需求内容和归属；避免 A 与 B 实际发布的是不同内容。原 READY/RELEASED 之间的展示可以用批次进度表达，避免额外向需求加入发布中阶段。具体 API/锁序需在实施前更新契约和状态机说明。

## 后续补发

版本整体上线后，可新增补发批次，例如首次 A、B，隔一周新增 C、D。每个批次保存独立计划和完成进度：首次完成 2/2，补发进行中 1/2，总覆盖 3 个目标。补发不重开已上线版本/需求，不重复发送全局“需求已上线”通知，不覆盖首次范围、操作人或时间。

后续批次新增目标，不通过编辑首次已完成批次抹掉历史。未开始的目标如需增减，需填写原因并保留变更记录；已完成目标不能移除、撤销成功或改写为未发布。批次目标不允许重复。是否允许对同一目标重发同版本，首版建议单独使用显式“重新发布记录”并填写原因，不能重复点击制造第二次成功。

版本详情展示累计覆盖目标和每批进度，可展开各目标历史。发布记录中提供目标筛选，便于回答“这个版本到过哪些小程序”“这个小程序最近登记的版本是什么”。实际发布时间与系统登记时间分开保存；补录时间允许填写，但不伪造审计时间或默认认为所有目标已经上线。

## 权限、并发和旧数据

目标目录沿用业务系统管理权限和范围；批次/目标成功登记沿用版本发布资格和 DataScope。主链发布仍使用专用原子事务、版本/需求锁序和 revision CAS。首次批次最后一个目标并发完成只能触发一次 Release/状态同步/通知；补发独立校验版本和批次 revision，并使用唯一约束避免重复。

历史 Release 不推断小程序范围，显示“历史发布，未记录目标”。历史已发布版本可从新补发批次开始记账，保留原 Release。历史未发布且未配置目标的系统应先配置目标或明确选择传统单次发布兼容路径，不能静默创建虚构目标。

实施拆分：目标目录与查询 → 批次及快照 → 首次完成事务与冻结 → 补发与历史查询 → 双数据库追加迁移/并发回归 → TEST 验收。涉及真实发布语义和数据库变化，应按本方案确认的业务规则逐项更新开发契约；不直接操作当前正式环境。
