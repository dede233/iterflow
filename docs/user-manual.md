# 迭程 IterFlow 操作手册

本手册面向公司成员、产品、设计、开发、测试和管理员，说明反馈到发布的日常操作。更新日期为 2026 年 10 月 10 日，适用于当前本地协作开发快照。按阶段分配人员、可选设计阶段和全员开发确认已经本地实现；本手册同步不代表这些功能已经升级到线上。使用前请由维护人员确认当前环境版本。

主流程是反馈转为需求，需求加入版本，完成开发与测试后登记成功发布，生成发布记录并同步上线状态。系统内的“发布”记录业务发布结果，不会自动部署应用服务器。

## 登录与个人账号

使用管理员提供的环境地址和个人账号登录。已有服务器入口为 https://sx-kc.xyz:8443；该地址不表示已经部署本手册的新功能。首次登录如要求改密，应先完成改密，再使用业务菜单。忘记密码联系维护人员，操作手册不保存初始密码或测试密码。

每人使用自己的账号。开发完成必须由本人确认，不能借用管理员或负责人账号。个人中心可以修改密码和退出登录；通知中心可以阅读消息和标记已读。离开共享电脑时退出登录。

## 角色与可见范围

下面是基础角色的默认职责。管理员可以配置角色组合；按钮可见不代表拥有全部操作权限，后端还检查权限码与数据范围。

| 角色 | 默认职责与边界 |
| --- | --- |
| 普通成员 | 提交反馈，查看自己范围内的反馈、需求、版本及发布记录；默认没有反馈编辑权限 |
| 客服运营 | 处理和编辑反馈；默认不能转为需求 |
| 产品负责人 | 转需求、编辑需求、分配人员、创建编辑版本、迁移需求；默认没有需求状态及发布权限 |
| 研发负责人 | 自己范围内的需求和版本编辑、状态推进；可作为开发候选，默认没有发布权限 |
| 开发人员 | 查看参与的需求，按权限推进需求状态，确认本人开发完成；不能默认分配人员或发布 |
| 设计人员 | 查看参与的需求，按权限推进需求状态；不能默认分配人员或发布 |
| 测试人员 | 自己范围内的需求与版本状态推进；默认不能分配人员或发布 |
| 超级管理员 | 基础管理、业务权限和发布；仍不能代替未绑定的开发人员确认完成 |

SELF 范围通常按本人创建、负责及业务关联判断；被分配为开发或设计人员会取得对应需求的参与可见性。参与需求不会自动授予权限码，也不自动取得其所属版本的可见性。ALL 范围允许查看全部相应业务记录。找不到记录时先检查登录账号、权限、数据范围和筛选条件。

开始设计或开发同时需要需求编辑、需求状态权限及该需求可见性。需要产品人员推进阶段时，管理员应配置相应角色组合，例如产品负责人兼研发负责人；不要只凭职位名称判断权限。

## 提交和处理反馈

在“反馈管理”提交反馈，填写标题、内容、所属系统或模块等页面要求的信息，需要时附上文件。提交成功后取得反馈编号，状态为“待处理”。系统和模块由管理员维护，模块应属于所选系统。

负责人查看反馈后点击“受理”，常规受理只需确认，不必填写原因。重复反馈应选择一条可见且不是自身的重复目标。无法复现、关闭以及重开必须填写非空原因，记录在审计中。

| 操作 | 条件和结果 |
| --- | --- |
| 受理 | 待处理转为已受理，无需原因 |
| 标记重复 | 待处理或已受理转为重复；选择重复目标，无需原因 |
| 无法复现或关闭 | 待处理或已受理可执行；必须填写原因 |
| 重开 | 重复、无法复现、已关闭转为待处理；必须填写原因，重开重复反馈会清除重复指向 |
| 编辑已关闭反馈 | 具备反馈编辑权限及可见范围时可保存；保存不会自动重开 |

已关闭反馈可以先编辑，再点击“重开”并填写原因。保留原编号和历史，不会创建另一条反馈。不能把已受理直接退为待处理。“已转需求”和“已上线”由对应业务事务产生，不能手工设置。

产品人员可把反馈转为新需求，也可归并到已有可见需求。多条反馈可以对应同一需求，一条反馈最多一个主需求。转换后核对反馈主需求链接、需求来源和状态；不要重复转换或直接修改数据库关系。

## 建立需求与按阶段分工

可从反馈转换需求，也可在“需求管理”直接新建。完善标题、描述、优先级和验收标准。优先级采用 P0 至 P4，公司应统一使用口径。验收标准应写明可判断通过或失败的结果。

需求保留一名总负责人，可绑定多名设计、多名开发。详情中先“设置总负责人”，不必在创建时提前选齐全部人员。常规流程为草稿、已确认、已排期、开发中、测试中、已完成、已上线；需要设计时，在已排期与开发中之间经过“设计中”。

需求确认并排期后，需要设计的点击“开始设计”，选择至少一名启用的设计人员后确认。不需要设计则直接“开始开发”，选择至少一名启用的开发人员。设计人员须具有设计角色，开发人员须具有开发人员或研发负责人角色，均须具备需求查看权限。

设计结束后“开始开发”，此时才选择开发人员；既有设计分工保留。开始阶段会把人员分配、状态变更、修订号、审计和通知一起保存，失败时不会只保存一部分。

设计中可以“调整设计人员”；开发中、测试中、已完成可以“调整开发人员”。总负责人单独设置，调整一组不会覆盖其他组。开发相关阶段不能用空开发名单绕过门禁。开始设计、开始开发的人员选择最多各 100 人，不允许重复。

暂停、恢复、取消按当前状态允许的按钮执行。设计中可暂停、取消或进入开发；没有独立“设计完成”审批或开发退回设计流程。“已上线”只由成功发布自动产生。

## 每名开发人员确认完成

开发人员登录自己的账号，在需求详情“协作人员”中点击本人完成确认。只有当前绑定、启用、具有开发资格且有需求查看和状态权限的人可以确认。开发中、测试中、已完成阶段允许确认；不能指定其他人代确认。

页面显示已确认人数，例如 0 / 2、1 / 2、2 / 2。全部开发人员确认后仍需按原流程提测、验收，再由有权限的人把测试中的需求标记“完成”。全员确认不会自动推进状态，也不替代测试验收。

进入“已完成”必须至少一名开发人员且全部本人确认。未满足时按钮禁用，直接调用接口同样返回业务冲突；管理员和产品人员也不能绕过。页面加载失败时先刷新，不应凭旧人数继续操作。

退回开发、重新开发或恢复到开发中会清空全部完成确认，返工完成后需要再次本人确认。仅调整人员名单时，保留在名单中的人员确认保留；新增人员、移除后再次加入的人员为待确认。已完成需求调整开发名单后，新人员待确认会再次阻断发布。

已完成需求在所属版本尚未发布时可以“重新开发”，必须填写原因。历史需求没有自动代确认；需要相关开发人员补充确认，或按合法流程返工。跨账号操作后刷新页面，避免继续使用旧修订号。

## 版本规划与需求迁移

在“版本管理”新建版本，填写唯一版本号、名称，以及可选计划上线日期和说明。版本初始为“规划中”。在版本详情添加需求；草稿或已确认需求加入版本后会自动排期，其他状态按规则处理。

版本按规划中、开发中、测试中、待发布推进。版本状态与需求状态分别维护，版本提测不会替代每条需求的测试验收或本人完成确认。

迁移需求时选择目标版本并填写原因。系统关闭旧有效关联、新建目标有效关联、更新当前版本并写审计；历史关系保留，同一需求同时最多一个有效版本关联。“移出”只调整当前关联，不删除需求。

待发布、已发布、已取消版本的需求清单冻结，不能新增、迁移或移出。待发布版本需调整清单时，先“退回测试”并填写原因。已发布是终态，后续变更建立新的版本。

已发布版本仍有“编辑”按钮，当前页面允许修改版本名称、计划上线日期和说明；接口还支持修改总负责人。编辑需要版本编辑权限、数据范围和最新修订号，记录审计。它不允许修改版本号、已发布状态、需求清单或已有 Release 的发布说明、结果和发布时间。该行为是当前实现，并非重新发布。

## 发布与结果核对

发布人员先确认实际部署与验收安排，再在版本详情进行发布前检查。基础产品、研发和测试角色默认没有发布权限，需要获授权的发布人员执行。

检查要求版本为“待发布”，全部有效关联需求为“已完成”，每条需求至少有一名开发人员且全员本人确认。无效历史关联不算当前清单；取消、暂停、测试中的有效需求也会阻断发布。检查失败时处理提示对应的需求或状态，再重新检查。

填写发布说明并提交。检查与实际发布执行相同门禁，实际发布重新检查并发变化。成功后系统在同一事务内生成 SUCCESS 发布记录，更新版本、需求、反馈、通知和审计；中途异常全部业务写入回滚。

| 核对位置 | 成功结果 |
| --- | --- |
| 版本详情 | 已发布，可查看实际发布时间和发布历史 |
| 发布记录 | 一条本次成功 Release，发布说明正确 |
| 当前有效需求 | 满足规则的需求变为已上线 |
| 关联反馈与通知 | 反馈显示已上线，相关提交人收到上线通知 |
| 审计中心 | 操作者、关键动作、对象及时间可追溯 |

请求超时或网络中断时先刷新版本和发布记录，确认实际结果再处理；不要立即重复点击发布。重复发布返回冲突。系统不提供撤销已发布或失败 Release 的入口，后续修复按新版本处理，不手工把需求或反馈置为上线。

## 通知 文件与多人编辑

阶段开始和状态推进按对应职责通知参与人员，并通知总负责人和创建人；成功发布继续通知相关人员和反馈提交人。同人兼任多职责会去重，操作者不接收自己触发的通知。通知指向的对象仍需权限及数据范围校验，收到通知不等于取得所有权限。

附件使用业务页面的上传、下载和删除入口，受文件权限与关联业务可见性保护。不能通过复制下载地址或更改 file_id 绕过授权。上传失败检查大小、网络和权限；存储异常交给维护人员，不手工修改文件元数据或磁盘路径。

保存、状态变更、人员调整和版本迁移都使用 revision 修订号。两人同时编辑时，先保存的人成功，另一人旧页面保存返回 409。先保留输入，加载最新对象，比较变化后重新编辑；不要自动重试覆盖。编辑提示仅提醒有人正在编辑，不是独占锁。

数据库保存 UTC，API 使用 ISO 8601，页面按本地时区显示。检索可用中文关键词、所属系统模块、状态和日期等页面提供的条件；定位异常时记录时间与时区。

## 十五步主链路核对

此清单用于培训及明确的隔离测试；不证明任一线上环境已验收通过。并发、重开、迁移和异常演练应使用独立测试数据。

1. 管理员登录，按提示完成首次改密。
2. 创建个人账号，配置成员、产品、设计、开发、测试及发布职责。
3. 成员提交反馈，取得编号和待处理状态。
4. 有权限的负责人受理反馈。
5. 产品人员转换为新需求，或归并到现有需求。
6. 设置总负责人，完善优先级和验收标准。
7. 将需求加入版本，核对唯一有效关联。
8. 按需开始设计，再开始开发分配开发人员；每名开发本人确认，测试验收后标记完成。
9. 版本推进至待发布，核对全部有效需求及全员确认门禁。
10. 发布人员填写说明发布，生成成功 Release。
11. 核对需求已上线。
12. 核对关联反馈已上线。
13. 反馈提交人查看站内上线通知。
14. 管理员核对关键动作审计。
15. 在另一条未上线的测试需求上执行双人编辑，旧 revision 保存必须返回 409。

补充核对多反馈归并、可选设计、0 / N 与 N / N 确认、返工清空、开发名单变更、迁移历史、重复发布、文件授权、异常回滚和重启持久化。保存业务编号、操作者、实际结果和异常证据。

## 常见问题与管理员维护

常规受理、确认、排期、提测等不要求原因；关闭、无法复现、反馈重开、需求重新开发、版本退回测试和版本迁移需要原因。是否显示输入框由实际业务动作决定，不必为每次状态推进填写重复说明。

“开发未确认却能完成”已在本地开发快照修复：后端同时保护需求完成与发布。若目标环境仍出现旧行为，先核对已部署代码、迁移版本及前端缓存，不把手册更新当成应用已经升级。

401 表示需要重新登录；403 表示权限或首次改密限制；404 可能是不存在或不可见；409 表示修订号、状态、关系或并发冲突；422 表示字段不符合契约。向维护人员提供页面、业务编号、时间及去除秘密信息的截图，不发送密码和 Token。

接口文档入口为桌面“系统设置 → 接口文档”，手机“我的 → 接口文档”，支持搜索和下载。只有启用的系统超级管理员或研发负责人可以读取，普通开发人员和产品人员默认不具备此资格。

管理员维护用户、角色、系统和模块，确保每个开发与设计人员账号启用且职责正确。现有用户管理页面没有密码重置入口，账号恢复由维护人员按明确流程处理，不通过重复 seed 或手改数据库恢复。

维护人员按目标部署包的运维说明执行健康检查、迁移、备份和重启；数据库与附件作为一组备份，升级前核对应用版本及迁移 head。现有库通过正式迁移升级，不重复基础 seed，不使用 create_all 或 stamp 绕过迁移。当前协作迁移 head 为 PostgreSQL 0007_development_completion，MySQL mysql57_0005。

恢复演练只使用独立测试库及测试附件存储。正式上线前清理测试账号和数据应另行制定空库初始化或受控切换方案；本次手册同步不清空账号、不操作服务器。密码及配置保存在受保护配置文件，测试数据库、密钥和附件不进入部署包。
