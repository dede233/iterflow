## 已核对的具体缺口

- `RequirementDetailView.vue` 在 `onMounted` 开始编辑提示并每 120 秒 heartbeat，`onBeforeUnmount` 结束；没有以打开/关闭编辑 Dialog 为边界，也没有使用 start 响应展示已有编辑者。后续应审查请求失败与页面离开时的清理。
- 后端 Feedback/Requirement/Version 冲突响应通常有 `current_revision`、`current_updated_at`、`current_updated_by`，但 `latest` 摘要只在部分路径（如系统目录）存在。V1.6 冲突 UI 必须逐接口核对并先定义安全的最小摘要契约。
- `NotificationCenterView.vue` 只对当前取回的 `rows` 计算未读数；Release 通知统一跳 `/releases`。现有测试 `NotificationCenterView.spec.ts` 验证先标已读再导航。
- `backend/app/api/v1/requirements.py`、`versions.py` 列表当前只有分页；相应前端列表也只发送分页参数。Release API 已有 `version_id`，但 `ReleaseListView.vue` 不提供该筛选。
- Dashboard 已有最近活跃版本和最近发布，缺跨实体最近动态；若不能证明对每条活动的对象权限与 DataScope，则推迟 Phase 6。

## 技术债、规格差异与风险

1. 当前 `spec/openapi-v1.5.yaml` 比正式 `v1.5.0` 标签版本多 369 行系统目录契约；动态/静态 parity 针对当前代码仍成立，但文件名已不能单独证明正式 V1.5 发布快照。历史契约应从 `v1.5.0` 标签取证。Phase 0 不改文件；首次 V1.6 API 变更时建立 `spec/openapi-v1.6.yaml`，并设计 V1.5 历史快照的归档方式，不覆盖历史。现有同步脚本、parity 测试和前端类型脚本仍指向 `openapi-v1.5.yaml`，首次 API 变更时须一起迁移。
2. 用户规划稿把 Editing frontend 写作“没有接入”、把 409 数据写作普遍含 `latest`；当前代码显示两项均需修正为上述 Partial。此为规划描述与实现现状差异，不是核心领域规格冲突。
3. 列表筛选及 Dashboard 活动可能跨越 DataScope；通知总数与全部已读必须严格按当前用户隔离，不能用前端按钮隐藏代替后端校验。
4. Presence 只是提示，Redis TTL 与网络中断可能造成短暂陈旧状态；不得将它升级为写入硬锁。Release 详情必须只读且保持原有 `rd.release.view` 和对象范围。
5. V1.5 主文档与现行 OpenAPI 对核心业务未发现需要本阶段中止的冲突；本轮未运行新业务测试，也未声称 V1.6 已交付。
