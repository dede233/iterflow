# V1.6 Phase 6 — Dashboard Activity 可见性证明

开发基线：master `b2b2dbe804231f946e54c0af596e3465290b83c3`。

## 入口与权限矩阵

最近活动沿用 `GET /api/v1/dashboard/overview`；入口继续要求 `dashboard.view`。业务域权限和对象 DataScope 必须同时满足：

| Entity | Required permission | SELF visibility | ALL visibility | Route |
| --- | --- | --- | --- | --- |
| FEEDBACK | `rd.feedback.view` | `Feedback.submitter_id == current_user.id` | 所有现存 Feedback | `/feedbacks/:id` |
| REQUIREMENT | `rd.requirement.view` | `Requirement.owner_id == current_user.id OR Requirement.created_by == current_user.id` | 所有现存 Requirement | `/requirements/:id` |
| VERSION | `rd.version.view` | `Version.owner_id == current_user.id OR Version.created_by == current_user.id` | 所有现存 Version | `/versions/:id` |
| RELEASE | `rd.release.view` | `Release.version_id → Version`，Version owner 或 creator 为当前用户 | 关联现存 Version 的现存 Release | `/releases/:id` |

Release 不以 `Release.created_by` 判断 SELF；链接使用 Release 自身 ID，不能替换成 Version ID。

`dashboard.view` 不扩大业务域权限。只有该权限时，四个原有业务 section 为 `null`，`activities` 为 `[]`。即使某个其他域的对象满足 SELF，没有其 `rd.*.view` 也不能看到该域活动。

`sys.audit.view` 不是安全活动摘要的前置条件，也不能替代业务域权限。`sys.user.view` 不需要：活动没有操作人展示或 User 查询。`*` 允许四个业务域，仍必须满足对象可见性；不能扩大到系统配置或账号审计。TEAM 保留原有 reserved 行为，本阶段只支持 SELF/ALL。

## 数据源、查询与严格投影

数据源为已有 `sys_operation_log`，不新增实体、表、migration、权限或审计写入。`AuditRepository.list_recent_scoped(...)` 只查询 OperationLog，复用原有 `_visibility_criteria(...)`，不 JOIN User。各业务域通过现存实体 ID 子查询过滤，因此 `entity_id = null` 和不存在的实体被排除；ALL 也不能绕过实体存在性检查。

DashboardService 仅按业务读取权限构造四域 allow-list，并明确投影为 `DashboardActivityItem`：

| 字段 | 来源 / 约束 |
| --- | --- |
| `entity_type` | FEEDBACK / REQUIREMENT / VERSION / RELEASE literal |
| `entity_id` | OperationLog 的实体 ID，非空 int |
| `action` | 原始审计 action code |
| `created_at` | OperationLog 原始时间 |

不返回 `operation_log_id`、`operator`、`operator_id`、`username`、`display_name`、`before`、`after`、`before_data`、`after_data`、`request_id`、`ip_address`、`user_agent` 或从审计详情生成的 summary。数据库拥有这些值也不会进入响应或页面。

USER、AUTH、ROLE、SYSTEM、DICTIONARY、BUSINESS_SYSTEM、BUSINESS_MODULE 均不进入该 allow-list。包括 wildcard 和同时拥有审计权限的用户。

排序固定为 `OperationLog.created_at DESC, OperationLog.id DESC`，最多 15 条；接口不新增数量参数、分页或历史入口。查询异常沿用 overview 的请求失败 / 500 处理，不捕获异常伪装成空活动。

## 与 Audit Center 的边界

`GET /audits` 和 `GET /audits/{id}` 继续要求 `sys.audit.view`；其既有数据范围和 AuditOut 保持不变，包括 operator、before、after。Dashboard 的独立最小 schema 不复用 AuditOut，也不放宽 Audit Center。

活动详情点击仍经过原有 Hash Router 与详情 GET 的权限 / DataScope 校验。权限或范围在 overview 加载后变化时，详情的 403/404 继续生效。没有新 route，也没有新增后台读取授权。

## 页面与契约

现有指标、状态分布、近期活跃版本与近期发布均保留，后面新增全宽“最近活动”。实体与动作复用 `auditEntityLabel` / `auditActionLabel`，未知动作显示 `未知操作（CODE）`；时间按现有本地时间格式显示。无日志时显示“暂无最近活动”，不隐藏其他概览内容。

仅 V1.6 契约新增必需的 `activities`、四字段 item 和四域 literal，重新生成前端类型并校验 runtime parity。两份 V1.5 静态契约继续保持五字段 overview，不改历史契约。
