# IterFlow V1.6 — 协作体验与信息可见性增强

## 产品目标与冻结边界

V1.6 在已发布 `v1.5.0` 和当前开发基线 master `f43f76145961b54d279cf3c85dd4afeb3e0e2d3f` 上，提高多人协作、冲突处理、通知效率、发布可追溯性、列表操作效率与工作台信息密度。当前事实与证据见 [基线审计](v1.6-baseline-audit.md)。

核心链固定为 Feedback → Requirement → Version → Publish → Release。Feedback 是外部输入，Requirement 是正式需求，Version 仅纳入 Requirement；Publish 是唯一发布入口，Release 是成功发布的记录而非工作流实体。继续遵守 `spec/status-machines.md`、revision CAS、事务边界、RBAC/DataScope。Hash Router 的 `createWebHashHistory(import.meta.env.BASE_URL)` 和 `/#/...` 是正式产品要求。

## 优先级与阶段

| 阶段 | 优先级 | 交付与验收重点 |
| --- | --- | --- |
| Phase 0 — Baseline & Docs | 完成 | 冻结已发布版本与开发基线，按代码/测试/CI盘点，建立规划和任务；仅文档。 |
| Phase 1 — Editing Presence | P0 | 复用现有 start/heartbeat/end 与 Redis key，在 Feedback/Requirement/Version **实际开始编辑**时 start，编辑期间 heartbeat，关闭 Dialog/离页 end；展示他人正在编辑但不阻止写入。修正需求详情当前“打开详情即开始”的语义。验证多用户、TTL、异常清理。 |
| Phase 2 — Revision Conflict UX | P0 | 逐接口核对 409 元数据并先确定最小安全摘要；显示更新人、时间、revision、服务器摘要，允许重新加载或关闭后人工处理，可安全保留本地输入供复制。禁止自动覆盖、强制保存。 |
| Phase 3 — Notification V2 | P1 | 规划 `GET /notifications/unread-count` 返回 `{ "count": n }` 和 `POST /notifications/read-all`；仅当前用户。桌面导航/移动 Bottom Nav badge 与通知中心总数、全部已读；保留先标已读再导航。 |
| Phase 4 — Release Detail | P1 | 复用现有 GET `/releases/{release_id}`，新增 Hash route `/releases/:id` 只读页，权限 `rd.release.view`，展示 ID、Version、Released At、Result、Release Notes、Rollback Notes、Created By/At；有 `rd.version.view` 才链接版本。有 ID 的 Release 通知进入详情，无 ID 的旧通知进入列表。 |
| Phase 5 — List Productivity | P1 | Requirement：编号/标题关键字、status、priority、source、current_version_id、owner_id；Version：版本号/名称关键字、status、计划发布日期范围、owner_id。后端强制 DataScope，前端桌面筛选栏/移动筛选抽屉，不做查询 DSL。Release 先接入已有 `version_id` 筛选，日期范围视成本评估；无 Release 工作流状态筛选。 |
| Phase 6 — Dashboard Activity | P2 | 优先复用 OperationLog/Audit，不建 Activity 实体；最多 10–20 条，仅显示当前用户对业务对象原本可见的反馈、需求、版本、发布活动。权限/数据范围无法清楚证明时延期。 |
| Phase 7 — Regression & Release Readiness | 门禁 | 核心主链、409 两人冲突、权限绕过、通知隔离、发布事务、Hash Router、五视口、六项 CI、OpenAPI parity、PostgreSQL 与部署回归；通过独立终审后再讨论 1.6.0 版本号与标签。 |

## 明确不做

TEAM DataScope；工时、Story Point、预计开发时长及报表；Release rollback workflow 或 Release 状态机；新核心业务实体；WebSocket 实时平台；微服务；独立移动 App；Feedback 直接加入 Version；AI 自动决策业务状态。不得借 V1.6 改动 Feedback/Requirement/Version 状态或 Publish 事务语义。

## 接口、契约与发布策略

Phase 0 不变更 API、代码、migration、权限或包版本。未来首次 V1.6 API 变更应先形成评审过的契约，再同步运行时 OpenAPI、静态文件、前端类型和测试；建立 `spec/openapi-v1.6.yaml`。当前 `spec/openapi-v1.5.yaml` 含发布后补充内容，正式 V1.5 历史应以不可变标签的文件为证；归档差异见基线审计。核心业务契约若与 V1.5 主文档冲突，按 `AGENTS.md` 停止并请求确认。

每阶段采用小步实现与测试报告。API 变化须通过动态/静态 OpenAPI parity；后端须通过 pytest、PostgreSQL-only、Ruff、format、Mypy、compileall、Alembic check；前端须通过 Vitest、API 类型检查、build/bundle；浏览器须保留现有 `/#/...` Playwright 和 375/390/768/1280/1440 响应式验收；部署须通过六项 CI。不得以绿色重跑掩盖首跑 flake。

`v1.5.0` 始终是当前已发布稳定标签；V1.6 当前开发基线为 master `f43f76145961b54d279cf3c85dd4afeb3e0e2d3f`。Phase 0 原始规划起点 `f6a20b82b432543de4cadb2309813f376a77eaa6` 记录于基线审计。Phase 0 规划在独立终审通过后进入开发主线；本阶段不创建版本标签，也不提前修改 backend/frontend 包版本。Phase 7 才统一评估 `1.6.0` 发布准备。
