## 3. 核心链、状态机与事务：继续冻结

**Feedback → Requirement → Version → Publish → Release**。Feedback 是原始外部输入；Requirement 是正式研发需求；Version 只容纳 Requirement；Publish 是唯一正式发布事务入口；Release 是成功发布记录。不得因文档遗漏 Publish 而改变业务模型。

### 状态机复核

实现源：`models/enums.py`、三实体 Service 的集中 transition map、Manual* schema；测试为 `test_state_machines.py`、各实体 API tests 和 PostgreSQL 主链/并发 tests。

| 实体 | 完整状态 | 人工 / 事务产出与退回规则 |
| --- | --- | --- |
| Feedback | NEW / ACCEPTED / REQUIREMENT_LINKED / ONLINE / DUPLICATE / CANNOT_REPRODUCE / CLOSED | 人工目标 NEW、ACCEPTED、DUPLICATE、CANNOT_REPRODUCE、CLOSED。NEW→ACCEPTED；NEW/ACCEPTED→DUPLICATE/CANNOT_REPRODUCE/CLOSED；后三者可重开→NEW。不能 ACCEPTED→NEW。DUPLICATE 要 duplicate_of_id 且目标可见非自身；CANNOT_REPRODUCE、CLOSED、重开要 trim 非空 reason。重开清除重复关联。REQUIREMENT_LINKED 仅 convert，ONLINE 仅 publish。 |
| Requirement | DRAFT / CONFIRMED / PLANNED / DEVELOPING / TESTING / DONE / ONLINE / PAUSED / CANCELED | 主流 DRAFT→CONFIRMED→PLANNED→DEVELOPING→TESTING→DONE；ONLINE 仅 publish。TESTING→DEVELOPING 允许；DONE→DEVELOPING 要 reason 且所在 Version 尚未 RELEASED。CONFIRMED/PLANNED/DEVELOPING/TESTING→PAUSED；PAUSED→CONFIRMED/PLANNED/DEVELOPING/CANCELED；DRAFT/CONFIRMED/PLANNED→CANCELED。ONLINE/CANCELED 无后续人工迁移。首次转需求直接 CONFIRMED；加入版本时按关系策略将适用状态规划为 PLANNED。 |
| Version | PLANNING / DEVELOPING / TESTING / READY / RELEASED / CANCELED | 人工主流 PLANNING→DEVELOPING→TESTING→READY；TESTING→DEVELOPING 允许，READY→TESTING 必填 reason；PLANNING/DEVELOPING/TESTING 可取消。RELEASED 仅 publish，RELEASED/CANCELED 终态。READY/RELEASED/CANCELED 冻结需求集合。 |

没有一条通用规则要求所有旁路状态都填写 reason；只按现有 schema/Service 指定的迁移要求审计。不建议改变任何状态机。

### 三项事务边界

| 事务 | 当前实现 | 覆盖与已知边界 |
| --- | --- | --- |
| Feedback→Requirement | `FeedbackService.convert`：新建或关联可见 Requirement、Feedback CAS、主需求回填/状态、关系、审计同一次 commit；失败 rollback。CREATE_NEW 与 LINK_EXISTING 的双域权限按 API 限制。 | `test_feedback_api.py`、`test_v1_e2e_postgres.py`、revision tests；不异步化主事务。 |
| Requirement→Version move | `VersionService.move_requirement`：锁定源/目标 Version 并重读关系、分别 scope/freeze 检查、Requirement CAS、关闭旧 active、新建目标关系、current_version_id、原因/审计、源目标版本 revision，同一 commit。 | `test_version_relation_postgres.py`、integrity migration tests、API tests；实际竞争依赖真实 PostgreSQL，不能只用 SQLite 证明。 |
| Version Publish | 版本 row lock + READY/revision 条件 UPDATE、Release SUCCESS、DONE Requirement→ONLINE、适用 Feedback→ONLINE、审计、Notification 同次 commit；前检通过不免除正式 publish 再检查。 | Phase 7 在真实 SQL 写完后分别注入 Version/Requirement/Feedback/Release/Audit/Notification 异常，快照全回滚，再用原 revision 发布成功。无独立 Release workflow 或独立 CRUD。 |

Revision CAS 在 `repositories/base.py` 的 `WHERE id AND revision` 原子 UPDATE 中递增；三个实体及跨表写入有专项覆盖。40910 元数据只返回 current_revision/current_updated_at/current_updated_by；前端用权限受控详情 GET 读取安全摘要，不在错误响应复制整个对象。`skipRevisionConflictAlert` 只抑制核心局部处理的 40910；`skipConflictAlert` 保留全 409 局部处理语义；普通业务 409 继续提示。

这些原则、RBAC/DataScope、Hash Router 均是冻结边界。涉及改变的候选必须标 **ARCHITECTURE DECISION REQUIRED**，不能自行纳入开发。

## 4. 权限、DataScope 与 TEAM 成本

API 先身份/权限，Repository/Service 再对象范围；前端路由和按钮不代替后端。有效角色提供 permission union，wildcard 被鉴权支持；范围有 ALL 时为 ALL，否则 SELF，但遇 TEAM 会直接拒绝，不能理解为自动回落 SELF。

| 域 | SELF 规则 | ALL 规则 / 特殊限制 |
| --- | --- | --- |
| Feedback | submitter_id=本人 | 全部可见，仍要对应权限 |
| Requirement | owner_id 或 created_by=本人 | 全部可见，仍要对应权限 |
| Version | owner_id 或 created_by=本人 | 全部可见，仍要对应权限 |
| Release | 经关联 Version 的 owner/creator scope | 仍需 rd.release.view，链接 Version 再需 rd.version.view |
| Dashboard / Audit | 对每个领域对象复用可见性 | dashboard.view 与 sys.audit.view 不代替 domain view；审计 global 配置只允许 ALL |
| User / Role / System | 用户本人信息；全局管理不能借 SELF 执行 | User角色分配、Role管理、System管理要求 ALL；System启用目录 view OR manage 不要求 ALL |
| Files | standalone 属主；业务附件依业务对象+关系授权 | 通用接口不能绕过业务附件权限；ALL 不代替下载权限 |
| Notification | 本人所有权 | ALL 不放宽所有权；外部 ID mark-read 是 200 no-op，不泄露他人记录 |

System 管理码自然包含目录读能力，但 view 不含写能力。System audit 需 sys.audit.view +（view OR manage）+ ALL；SELF 不看 global config audit。关系接口要求相关双域权限，各对象独立校验范围。

### TEAM：HIGH / ARCHITECTURE，建议 DEFER

`schemas/role.py` 的 ConfigurableDataScope 仅 SELF/ALL；`UserRepository.data_scope()` 真实读 TEAM 抛 `TEAM data scope is reserved and unsupported in V1.5`。文本版本旧，但 V1.6 仍无 TEAM 支持；`DashboardService` 也显式拒绝。数据表/前端下拉补一个值远不足够。

若后续证明组织协作需求，必须逐项设计：

| 工作面 | 必须解决的模型 / 安全 / 验收问题 |
| --- | --- |
| Team / Organization | Team 实体、租户或组织边界、是否层级、禁用/删除历史策略 |
| User↔Team membership | 一人单团队还是多团队、有效成员/角色、成员变更权限与审计 |
| 对象 team ownership | creator team / owner team / 显式 owning team；创建时快照还是动态派生 |
| Feedback / Requirement / Version | 每个对象团队范围、跨团队转交、owner/team变化、列表/detail/CAS和关系操作一致 |
| Release through Version | 历史 Release 随 Version 当前 team 还是发布快照团队可见，不能越权 |
| Dashboard / Audit / Attachments | 查询、计数、最近活动、审计及文件下载同一套对象范围；global config audit 不自动开放 |
| User administration / role data_scope | 谁能看成员/授予团队角色，多角色/多团队组合优先级，SUPER_ADMIN保护 |
| 跨域双权限 | convert/link、版本加入/迁移/发布等须同时满足两域权限与团队范围，不只检查一侧 |
| Migration / seed | 新 FK、索引、历史对象回填、membership seed、无团队用户/对象兼容、回滚方案 |
| OpenAPI / Frontend admin UI | DTO、role范围、团队管理/选择器与权限、安全错误行为 |
| 测试矩阵 | SELF/TEAM/ALL × 单/多团队 × 层级 × 跨团队 × 历史成员变更 × 三事务 × 附件/审计/统计 |

未明确：是否多团队、是否层级、对象归属依据、转交规则、Team 调整是否追溯影响历史数据。没有业务规模/流程证据支持价值。C5 同时需要产品与架构决策，默认不纳入推荐 V1.7 产品范围。

### Deprecated permissions

- `sys.role.edit → sys.role.manage`、`rd.requirement.version.move → rd.version.edit` 仍在 seed 和 PermissionCatalog。重复 seed 不删除，SUPER_ADMIN 包含全部 seed codes；PRODUCT_MANAGER / DEVELOPMENT_LEAD 仍 seed 旧 move code，所以角色确实可能持有。
- 前端 PermissionAssignmentDrawer 显示旧 code、已废弃标签与 replacement_code；自定义角色可以选择，非只有历史隐藏项。系统角色整体只读。
- API 鉴权使用新 code，不把旧 code 当 alias。全源搜索旧 code 在产品后端只有 seed/catalog 引用；`test_role_api.py::test_deprecated_role_edit_permission_has_no_write_capability` 明确旧 role.edit 没有写能力。V1.6 OpenAPI 没有旧 code 字面引用，但 PermissionOut 保留 deprecated/replacement_code 字段。
- 本轮没有扫描真实数据库内每个自定义角色或输出授权清单；源码/seed 已能证明存在持有可能，不声称线上实际持有数量。
- 建议保留 deprecated catalog/payload 兼容，不恢复旧权限写能力。删除要先制定角色使用盘点、系统 seed同步、旧客户端 permission_ids 兼容、迁移与回滚、replacement 权限确认方案；不得自动将无权旧角色升级为新管理权限。

## 5. Release Productivity：只读查询候选

事实：`api/v1/releases.py` / `ReleaseQueryService` 当前仅 page/page_size/version_id；前端 ReleaseListView 仅“版本 ID”。按 released_at DESC、id DESC 排序；count 与 rows 共用条件；范围经 Version owner/creator。`Release.result` 只有 SUCCESS。V1.6 Phase 5 日期结论是 DEFERRED，不能改写成已有功能。

### released_from / released_to 评估

- 用户价值：按发布周期找实际发布记录，减少依赖记忆内部版本 ID；来自明确延期项，价值合理但需产品确认，不等于已经批准。
- 成本 LOW–MEDIUM：Router datetime 校验、QueryService 在 count/items 同步加 AND、静态契约/类型/API、桌面+移动日期组件与测试；不碰 Publish 和 Release 状态。
- 权限保持 rd.release.view，范围继续经 Version；不额外要求 User/Version view 才能查询，不允许日期筛选扩大 scope。
- 建议契约为带时区 ISO 8601 datetime，released_from 与 released_to 均含边界（>= / <=），允许单边；反向区间/无时区输入以明确 422 策略处理。待评审决定精确校验规则后再实现，不让服务端猜本地时区。
- UI 若按本地“日期”选取整天，应使用真实本地日期边界转 UTC。闭区间方案必须定义能表达下一本地日开始减 1 微秒的序列化规则，不能仅依赖 JS Date 的毫秒精度；另一方案是 API 明确的右开区间、上界取下一本地日开始。两者必须择一冻结，不能混用 date 和 datetime、用 23:59:59 排除分数秒，不能假设所有本地日均为 24 小时。精确时间查询与整天选择的区别须一起评审。
- 数据库 Release.version_id 唯一约束提供相关索引；无 released_at 专用或 (released_at,id) 复合索引。缺索引是潜在增长风险，不是已证明慢查询。优先无 Migration；若 representative PostgreSQL EXPLAIN/延迟证据要求索引，应独立确认 migration，不默认加。
- 测试必须包含单/双边、精确边界/分数秒、不同 UTC offset/本地日/DST、反向区间、空结果、稳定排序/分页与 total、SELF/ALL/无权限、移动 Popper 可见性和 leave transition 结束后的 overflow 测量；复用已治理的 visible Popper/poll 策略。

## 6. 过滤语义

Feedback Router 已 trim 空白；Repository 直接 `like = f"%{keyword}%"`，对 feedback_no/title/description ILIKE，% 和 _ 为 wildcard，未显式 escape。Requirement/Version trim 后按编号/标题或版本号/名称匹配，并转义反斜杠、%、_，显式 escape；不搜索描述。

这是 **Filter semantic inconsistency**，参数仍通过 SQLAlchemy 绑定，不能据此判为 SQL injection。建议 V1.7 统一“literal substring”，保留各实体既有搜索字段。C3 是一致性 bugfix 意图，同时是外部可观察的 **contract behavior change**；旧使用 wildcard 的客户端会改变结果，不能伪称完全无行为变化。须评审记录 query 语义并增加 Feedback %/_/反斜杠、大小写、trim、description、组合 DataScope、分页 total regression；现有 Requirement/Version literal tests 保留。

## 7. Notification / Dashboard / Audit

### Notification freshness

未读 count 独立查询所有本人未读记录，不只数页面（列表最多 100）。read-all 数据库更新全部本人未读，幂等；前端 generation/session 防止已读/换用户后的旧响应覆盖。AppLayout 初始化、通知中心 load、mark-read、read-all 更新共享状态。没有自动服务器实时推送或 focus/poll 刷新。

建议 C6 优先可见窗口重新聚焦时刷新（去重、冷却、会话检查、失败保留当前计数）；页面导航刷新可作为备选但会增加请求。若真实需求要求不切换窗口仍更新，再评估 30–60 秒可见窗口 polling，hidden/offline/logout 停止，不能与 existing generation 互相打架。No WebSocket platform / SSE infrastructure / message broker。

### Dashboard Activity 边界

最多 15 条；OperationLog 源经 AuditRepository 对象可见性过滤，仅 FEEDBACK/REQUIREMENT/VERSION/RELEASE；只 entity_type/entity_id/action/created_at。需要 dashboard.view + 对应 domain view + SELF/ALL。不要求 sys.audit.view/sys.user.view，不返回 operator、before、after、IP、UA。复用可见性 SQL 不等于复用管理审计 DTO；不得从 Audit 详情拼装 Dashboard。

### Audit Center

page/size（最多 100）、entity_type/entity_id/action/operator_id/time_from/time_to；时间闭区间。列表/详情共享对象可见性 predicate，operator 最小 id/username/display_name，before/after JSON；IP/UA 未在公开 AuditOut 输出。sys.audit.view + 对应 domain view；SELF 看自己的业务对象与 USER/AUTH，ALL 才看 global config（System view OR manage）。

已有筛选、分页、详情、中文映射，没有证据要求新增审计导出、把 Audit 改普通活动流或开放更多字段。AuditCenterView 的异步 list/detail 未使用 sequence，潜在旧响应覆盖问题见第 10 节；这应是小范围正确性候选，不能放宽授权。

## 9. Preview 基础设施候选（不是产品缺陷）

## 10. 前端架构与具体正确性候选

- Vue3/Pinia/ElementPlus 单工程，router 继续 `createWebHashHistory(import.meta.env.BASE_URL)`，`/#/...` 及导航守卫冻结；auth/notifications 为共享 stores。
- API DTO/types 来源仍为 `spec/openapi-v1.6.yaml`，generated types 与 check:api-types；未来 V1.7 API 变更先评审新版本契约策略，不在本轮创建/改契约。
- useEditingPresence 用串行 queue 保证 start/heartbeat/end 的顺序，失败只影响提示；useRevisionConflict 用 sequence 对旧 preview/reload/close 结果作隔离。实体详情中仅实际写入口 suppression40910，未接入页面保留全局fallback。
- Requirement/Version/Release 三列表重复少量 filter状态、load sequence、重置page、卸载失效模式；共享 ListFilterPanel 已统一桌面/移动筛选，useResponsive 统一 767/768/1200断点。暂未证明这三处重复导致错误，不建议通用query框架/大规模DRY。业务过滤字段/日期/权限应留各页面。
- **静态可复现正确性债务（C8）**：`api/client.ts` silent refresh失败 catch 使用 `window.location.pathname` 比较/构造 `/login?redirect=...`。例如 `https://example.test/#/requirements/42?tab=info` 的 pathname 是 `/`，会生成 `/login?redirect=%2F`，丢失 Hash 业务目标且离开规范 `/#/login` URL。正常 Router guard 使用 to.fullPath，问题局限该 fallback 分支。本轮核对源码/URL解析，未在真实会话强制过期 token或执行 E2E复现。应增加 expired access + failed refresh 的 Hash目标回跳测试；修的是URL构造，不是更换Router mode。
- **潜在 async风险（C9）**：FeedbackList / AuditCenter 的 list请求没有三新列表的 sequence保护；AuditCenter showDetail 的 A慢/B快请求可能晚覆盖新选择，close后也缺失效保护。源码可见防护差异，本轮没有注入延迟证明生产复现，不称既定线上故障。建议先受控异步测试，再决定小范围修复，共享机制只在能降低正确性风险时抽象。
