# 流程入口检查（2026-11-03）

用户指出，之前需求确认时“提交后才提示未分配人员”的问题可能也存在于其他环节，要求检查。本轮仅检查、复现和记录，不修改产品实现，不访问线上数据库，不部署。

检查基线：工作分支 `codex/requirement-summary-no-progress`，HEAD `18ded78`；其中产品代码与正式冻结源码 `96ba96e` 相同。按现有开发契约、`spec/status-machines.md` 及协作流程方案核对，没有引入新的人员规则。

## 已确认的问题

### 1. 提交验收缺少完整的前置条件引导（P2）

开发人员存在且当前用户有操作资格时，即使没有有效验收人、启用的设计尚未完成，或当前内容确认已经失效，“提交验收”仍可打开普通原因弹窗并发送请求。后端分别以“请先指定验收人”“请先完成设计或说明取消设计的原因”“当前内容尚未确认”返回 409，弹窗继续留在原处；没有直接修正人员或设计的入口。内容失效已有页内警告，但按钮和提交检查未与之联动。

证据：`frontend/src/components/RequirementProgress.vue:81` 仅检查当前操作者的 DEVELOP 资格；`frontend/src/views/requirement/RequirementDetailView.vue:80` 仅按静态 needsReason 校验原因。后端实际前置条件在 `backend/app/services/workflow_service.py:88`。

建议：操作前列出当前阻塞项；缺验收人时，有人员编辑权限者直接进入验收人选择，无编辑权限者显示联系人员；设计未完成时显示当前设计状态及对应操作入口；内容失效时引导对应确认人重新确认。保存人员后返回原流程，由用户显式提交验收，保留后端实时校验。

### 2. 管理员代操作的原因未按实际资格设为必填（P2）

系统管理员／研发负责人不是指定开发或验收人员时，仍可打开“开始开发”“提交验收”“验收通过”弹窗，但原因无必填标记，空值直接发到后端并返回 403。现有代码还把具体的“管理员代操作须填写原因”统一替换为“你没有权限执行该操作”，用户难以判断如何继续。同类资格判断也应覆盖恢复开发、重新开发与验收退回；这些动作已有通用原因必填校验，本轮未发现它们能空原因提交。

证据：`frontend/src/views/requirement/RequirementDetailView.vue:74` 直接使用常量 actions 的 needsReason；`frontend/src/constants/requirement.ts` 对正常正向动作均为 false；`frontend/src/api/client.ts:95` 丢弃具体 403 说明。后端 `WorkflowService.actor` 强制分配有效人员及代操作原因。

建议：统一计算实际执行人、环节人员、是否代操作和原因要求；弹窗明确显示“代操作原因（必填）”，提交前阻止空值。对已识别的业务拒绝保留具体说明，其他权限错误继续按既有规则处理。不得取消管理员原因或人员门禁。

### 3. 反馈代受理没有原因输入入口（P2）

反馈已指定接收人，具备反馈编辑资格的管理员不在接收人列表时，“受理”弹窗只有确认文字，没有原因输入框。请求始终发送 reason=null，因此这个入口无法完成合法的管理员代受理，并显示泛化的权限错误。普通非接收人也能看到受理按钮，直到请求后才被拒绝。

证据：`frontend/src/views/feedback/FeedbackDetailView.vue:474` 仅在静态 needsReason 为 true 时渲染原因框；受理常量为 false。后端 `backend/app/services/collaboration_service.py:209` 要求非接收人的管理员填写原因。

建议：根据已读取的接收人及当前资格设置受理入口；指定接收人按正常流程受理，管理员代受理展示原因必填，其他人显示由接收人受理的说明。历史未设置接收人的反馈继续遵循已有兼容规则。

### 4. 后续环节缺人时仅隐藏按钮，缺少说明（P3，体验问题）

待开发没有有效开发人员时，“开始开发”直接消失。卡片虽显示“待分配”并保留“选择 / 调整人员”，操作区没有解释不能继续的原因；无人员编辑权限的用户也没有联系谁处理的指引。缺有效验收人员或设计人员的其他环节采取相似的隐藏方式。确认阶段已经有明确说明，其他阶段尚未统一。

证据：`RequirementProgress.vue:81` 的 actions 过滤、`:88` 的 designActions，以及仅针对确认阶段的提示。375px 与 1440px 已复现待开发缺人场景；其他缺人入口由代码核对确认。

建议：仍按权限控制真实操作入口，同时展示具体缺失环节及修正入口。有编辑权限者进入相应人员弹窗，无编辑权限者获得联系有人员编辑权限成员的说明。

## 已核对的正常边界

- 后端继续校验当前环节、有效人员、实际操作者、确认内容及原因；以上前端问题没有绕过这些规则。
- 多人验收仍为任意一名有权限的有效验收人通过即可，不是逐人会签。
- 退回开发、重新开发、暂停、恢复和取消的原因门禁在本地服务校验中正常；状态合法性、版本已发布限制仍由现有业务服务校验。
- 版本发布已有前置检查，并与实际发布共享校验服务；本次回归覆盖发布阻断、权限、revision、重复发布、事务回滚及状态同步，未发现同类“缺少人员输入导致无法提交”的新增问题。
