# 状态机

## 发布覆盖记录（2026-11-10，替代原目标计划规则）

版本正常通过 POST /versions/{id}/publish 发布，仍原子生成唯一 Release、同步需求/反馈 ONLINE 并通知；同系统已发布目标可选，不作为上线门槛。发布时选择目标与主发布同事务，发布后补记仅追加实际覆盖及审计，版本 revision CAS，不改原 Release/上线时间或重复全局通知。成功记录不可改写、重复或撤销。

旧批次及成功快照保留只读，旧计划写接口返回409。正常发布时将旧未完成计划关闭（保留成功行、未完成行仅标记未发布），不推断发布范围。旧不可逆冻结标记保留兼容并允许正常发布；新流程不产生部分冻结。不新增迁移，不回填旧版本系统或目标，历史无系统版本补记须明确目标系统且后续保持一致。

## Feedback

完整状态：`NEW, ACCEPTED, REQUIREMENT_LINKED, ONLINE, DUPLICATE, CANNOT_REPRODUCE, CLOSED`

人工可设置状态（`ManualFeedbackStatus`，经 `PATCH /feedbacks/{id}/status`）：`NEW, ACCEPTED, DUPLICATE, CANNOT_REPRODUCE, CLOSED`

合法人工迁移（其余一律 HTTP 409）：

```
NEW       -> ACCEPTED
NEW       -> DUPLICATE          (需 duplicate_of_id)
ACCEPTED  -> DUPLICATE          (需 duplicate_of_id)
NEW       -> CANNOT_REPRODUCE   (需 reason)
ACCEPTED  -> CANNOT_REPRODUCE   (需 reason)
NEW       -> CLOSED             (需 reason)
ACCEPTED  -> CLOSED             (需 reason)
DUPLICATE         -> NEW        (重开; 需 reason; 清空 duplicate_of_id)
CANNOT_REPRODUCE  -> NEW        (重开; 需 reason)
CLOSED            -> NEW        (重开; 需 reason)
```

- `ACCEPTED -> NEW` 明确不允许。
- `reason`（trim 后非空）在 `-> CANNOT_REPRODUCE`、`-> CLOSED` 与所有重开（`-> NEW`）时必填；仅保存在 `STATUS_CHANGE` 审计中，不新增数据列。
- `-> DUPLICATE` 时 `duplicate_of_id` 必填，须为存在、非自身、且操作者数据范围内可见的 Feedback。
- Feedback 是外部输入记录，不承担研发状态机；不得出现或同步 `PLANNED / DEVELOPING / TESTING`。
- `REQUIREMENT_LINKED / ONLINE` 事务产出状态禁止人工设置；请求体使用 `ManualFeedbackStatus`，因此提交这些值直接 422。
- 待处理反馈在详情可直接「受理并转需求」。复用新建表单或关联已有需求，提交到专用 `accept-and-convert` 接口，同时验证受理和转换权限、接收人资格、revision 及相关数据范围。代受理须填写原因。受理人、处理人、时间、主需求和关联状态在同一事务保存，并记录实际操作、生成现有反馈关联及新需求通知事件。
- 历史已受理反馈可继续通过转需求完成关联。保留独立受理接口以兼容既有调用，工作台的新受理入口使用联合操作。批量页面引导逐条打开反馈详情受理并转需求。
- `REQUIREMENT_LINKED` 仅由 Feedback→Requirement 转换事务产生（Phase 4）。
- `ONLINE` 只能由 Version 成功发布事务自动产生，普通状态接口任何情况下都不能设置。
- 有反馈查看权限的提交人可修改本人处于 `NEW`（待处理）的反馈内容。反馈进入后续状态后，仅按既有编辑权限处理。
- 所有写操作提交 `revision`，旧 `revision` 返回 409（乐观锁，禁止静默覆盖）。

## Requirement
DRAFT（待确认） -> CONFIRMED（待开发） -> DEVELOPING（开发中） -> TESTING（待验收） -> DONE（待发布） -> ONLINE（已上线）

2026-10-31 授权的新工作流：PLANNED 仅保留历史读取枚举，迁移为 CONFIRMED，不再接受人工写入。直接创建／反馈转新需求从 DRAFT 开始；加入版本不改变需求状态。确认、开始开发、提验、验收分别由具备权限的对应环节人员操作；人员分配不等于确认。修改 description／acceptance_criteria 增加内容版本，旧确认失效，继续正向流转或发布前须确认当前内容。设计为可选子进度，启用后提验前须完成或有原因取消。

待验收退回开发、暂停、恢复、取消均记录原因；暂停恢复目标只允许 CONFIRMED／DEVELOPING。2026-11-04 Issue #4 增量允许 CANCELED 经 workflow REOPEN 返回 DRAFT：原因必填，所属版本已发布则拒绝，清除当前确认资格和暂停来源，保留人员、关联与真实历史；ONLINE 不可重开。历史已完成需求保留发布资格，缺失的确认人和时间不得伪造。发布前检查与正式发布均检查当前内容确认资格。

旁路：CONFIRMED/DEVELOPING/TESTING 可进入 PAUSED；DRAFT/CONFIRMED/PAUSED 可按规则取消。

- `ONLINE` 只能由成功发布事务自动产生，普通状态接口禁止设置。
- 有需求查看权限的创建人可修改本人未冻结且处于 `DRAFT`（待确认）的需求内容。反馈转出新需求时，实际执行转换的账号是需求创建人。需求进入后续阶段后，仅按既有编辑权限处理。
- `DONE -> DEVELOPING` 仅在所属 Version 尚未发布时允许，必须填写原因并写审计日志。

2026-10-31 用户明确选择新方案：取消逐人开发完成确认。任一有权限的开发参与人可提交验收，指定验收人确认 DONE；原开发确认接口下线，原确认时间保留历史表与迁移步骤快照，不再参与 DONE/发布门禁。主状态 PLANNED/DESIGNING 都映射到 CONFIRMED，原 DESIGNING 保留为 IN_PROGRESS 设计子进度；不伪造确认/验收人员。

选人时可将选中的开发人员加入验收名单，保留已指定的其他验收人。名单按现有参与关系保存。开发中需求可通过 `workflow` 的 `COMPLETE_AND_ACCEPT` 一次提交开发完成及验收通过。操作者须同时是有效开发人员和验收人员本人，并拥有状态操作权限及需求数据范围；管理员代操作须走各自原有的环节入口。校验仍包括当前内容确认、设计完成或无需设计、发布冻结及 revision。事务内写入两条真实流程记录和带实际操作者的审计，只发送验收通过相关通知，最终需求进入 DONE（待发布）。普通状态接口仍按相邻阶段流转。

### 上线后确认与反馈

需求发布进入 ONLINE 后，其创建人可按当前 revision 确认一次线上效果。确认是上线后的实际验证记录，保存操作者、时间和选填说明，不改写发布或需求主状态。历史需求允许创建人实际确认，不为历史记录补造确认。可查看需求并有提交反馈权限的成员，可对该需求提交独立 NEW 反馈。线上反馈关联与需求的原始反馈及主需求关系分开，列表按反馈权限与 DataScope 返回；记录可走常规受理和修复需求流程。线上反馈关联已有修复需求时，目标须未上线且未取消。

## Version
2026-11-04 用户批准：版本进度由有效关联需求自动汇总，人工仅取消或正式发布；不再手动推进开发/测试/READY或退回版本阶段。API有效状态仍使用原枚举，历史非终态存储保持读取兼容但不是当前进度来源。

- 空清单为PLANNING；全部DONE且内容确认有效为READY；全TESTING/DONE但未就绪为TESTING；已开始工作但混有其他未完成项为DEVELOPING；其余为PLANNING。PAUSED/CANCELED需求不被静默忽略，异常ONLINE需求不取得发布资格。
- 全局进度、列表筛选及统计采用同一只读派生规则，不触发数据库写入。原RELEASED/CANCELED终态保持。
- READY为可发布提示，允许通过原权限、双revision和审计的清单接口继续调整；仅RELEASED/CANCELED冻结。调整后重新汇总。

- `RELEASED` 只能通过 `POST /versions/{id}/publish` 进入，普通状态接口禁止设置。
- 旧手动版本阶段接口仅接受取消未发布版本；推进或退回阶段返回409并引导操作需求。
- V1.5 MVP 仅支持成功发布；发布固定生成 `Release.result = SUCCESS`。
- `RELEASED` 为终态。发布必须通过独立事务执行 Release + Version + Requirement + Feedback + Notification 同步。
- 终态限制状态与有效需求清单；当前版本基础信息编辑仍允许修改名称、负责人、计划日期、描述，须权限、范围、revision CAS 与审计。已有 Release 记录不被此编辑改写。用户操作见 `docs/user-manual.md`。

## Concurrency
关键对象写操作必须提交 `revision`。旧 revision 写入返回 HTTP 409，禁止静默覆盖。

## 2026-11-02 多人验收与确认后安排人员

- ACCEPT 可指定多人，任意一名有权限的有效验收人员通过即可 TESTING → DONE，不进行逐人会签；退回仍须原因。2026-11-04 Issue #4 将 CONFIRM 同样扩展为多人、任意一名有效且有权限的确认人确认即可；本节下述单CONFIRM迁移约束为历史基线。
- 提交验收通知所有验收人员，邮件遵循验证与偏好；确认记录保留实际操作者和当时人员快照。并发或重复确认不得重复推进状态、写记录或发通知，旧 revision 返回 409。
- 新增需求及反馈转新需求须至少指定一名有效需求确认人。关联已有需求沿用目标的环节人员。确认当前内容前须有有效确认人、开发人员和验收人员。缺少人员时，有人员编辑权限的操作者可先补齐，再由符合资格的人员确认。仅保存人员不流转，重新确认不改变已有阶段。此前已流转的需求在执行相关动作时按现有阶段检查，不批量补写人员或历史。
- 追加 0012_multiple_acceptance / mysql57_0010 仅放开 ACCEPT 唯一约束，保留 CONFIRM 唯一约束及全部历史行；已有单人验收无需补写。存在多人有效验收时拒绝降级，不自动删人。MySQL DDL 升级需停止写入并备份；本次仅隔离验证。

## 2026-11-04 Issue #4

- CONFIRM 单人数据库约束由追加迁移 0014_issue4 / mysql57_0012 取消；旧参与人行及快照保留。并发确认仍只有一个 revision 成功，不重复记录和通知。
- 需求描述明确 PLAIN/HTML 格式；旧数据默认 PLAIN，HTML 经白名单清洗。修改内容格式也使当前确认失效。标题、描述不能保存为空白或仅不可见内容，创建、编辑和反馈转需求均校验。
- 反馈与需求的软删除沿用当前编辑权限，也允许有查看权限的创建人纠错。仅从未受理的 NEW 反馈、从未确认的直接创建 DRAFT 需求可删除，且无业务关联或历史引用。
- 批量需求动作支持确认、CONFIRMED→DEVELOPING、DEVELOPING→TESTING、TESTING→DONE；反馈支持NEW→ACCEPTED及NEW/ACCEPTED→CLOSED。逐项执行原门禁与事务，返回成功或失败明细，最多50条，不批量发布或自动重试。

## 2026-11-04 版本集中提交验收

- 用户明确选择省去逐步点击，已确认需求可直接提交验收，仍须验收人实际确认。版本页面可集中选择当前有效关联的需求，使用专用 `POST /versions/{id}/requirements/submit-acceptance`。
- 仅此入口允许 `CONFIRMED → TESTING`，要求填写至少2字符的原因；`DEVELOPING → TESTING`继续正常提验。普通状态接口及原批量接口的相邻阶段限制不变。
- 每项须有有效开发和验收人员、当前内容确认有效、设计已完成或明确无需设计，由有权限的开发人员操作；既有管理员代操作仍须原因。人员分配不等于内容确认、设计完成或验收通过。
- 逐项锁版本后锁需求，校验双方DataScope、版本及需求revision、未发布/取消和当前有效关联；一项失败不写该项状态/步骤/审计/通知，已成功项保留。版本进度仍自动汇总。
- 快捷提验仅记录真实的CONFIRMED到TESTING、操作者、原因和shortcut标记，不补造DEVELOPING事件或他人确认。提交后仍由有效验收人执行TESTING→DONE，实际发布仍走Publish事务。

## 业务系统绑定（2026-11-05）

新建版本必须指定有效业务系统，版本号仍全局唯一。创建并关联、单个/批量加入、迁移及变更系统必须保持版本与有效需求同系统，后端在既有事务、锁和 revision 内校验。版本修改先锁版本再锁有效需求，需求修改沿用版本→需求锁顺序。集中提验与发布检查再次校验同系统，不自动验收或发布。

旧版本通过可空字段兼容，迁移不推断或回填。归属未补齐时阻止新增关联、集中提验和发布，提示先编辑需求系统，再补齐版本系统；冲突需求可按原权限移出/迁移后处理。不静默修改其他实体，RELEASED/CANCELED 版本和 ONLINE 需求不能变更系统，历史 Release 不重写。停用系统允许历史读取和无关字段编辑，不允许新建归属或新增关联。

独立需求允许未指定系统；带模块时必须有系统且模块启用并属于所选系统。反馈已归属业务系统时，转新需求继承其系统和模块。反馈未指定系统时，可在转换表单为新需求选择一个已启用系统，或留空。归属随新需求在转换事务中保存，原反馈保留原归属。关联已有需求的反馈归并策略保持原规则，本轮不增加跨系统反馈归并限制。业务系统管理页及反馈新建/编辑/详情/筛选均隐藏模块入口，保留历史数据及后端兼容；反馈普通编辑保留历史模块，变更所属系统时清空旧模块。

### 运营协作抄送

物料制作和商家广告可选择多个启用账号作为抄送人。每次加入抄送和状态实际变化时，向对应人员发送站内通知，同一操作按收件人去重。移出后停止该记录的抄送提醒。抄送人从通知进入单条只读详情，可查看进度和该记录的图片。后台按当前关系鉴权，原本无权查看的人员被移出后再打开旧链接时会被拒绝。目录、列表、人员查找、编辑和状态处理继续使用原有权限与数据范围。

物料制作和商家广告的发布人持有对应类型的查看、发布权限并满足记录数据范围时，可更正本人尚未完成记录的标题、内容、截止时间、图片和抄送名单，并可查询抄送选项。仅在未开始时可更换有效接收人。发布人更正保留原工作日期、发布人、状态及处理信息，使用 revision 校验并记录实际操作者。更正商家广告接收人时通知新接收人，与同次抄送通知按收件人去重。已有编辑权限的账号仍按既有规则处理状态和编辑制作需求。

## 纠错删除与制作撤回

- 五个模块的删除都保留原始行、附件及审计，普通列表、搜索、统计、详情和新关联排除已删除记录。需验证数据范围、资格、原因和 revision，并记录实际操作者。已用编号继续保留。
- 物料制作和商家广告的发布人可删除本人未开始且从未处理过的记录。已选接收人和抄送人不影响纠错资格。进行中或邮寄中的制作可由发布人带原因撤回，状态为 WITHDRAWN，记录仍可查看，通知接收人和抄送人。已完成或已撤回的记录保留。
- 版本创建人可删除规划中且从未关联需求、没有发布历史的本人版本。有历史关联的版本沿用既有取消流程，已发布版本保留。
